## 1. Problem Statement

Enable founder to refresh any ritsu-works leaf entity (skill | command | agent | sop) from verified external information via `/update <type> <name> --refs=<refs>`, achieving ≥10 successful runs with ≥80% non-revert rate by 2026-06-30, with citation spine + Karpathy K4 quality ratchet (mode-aware ±5pt slack) guarding against regression.

**The trinity it completes:** /cla creates capabilities, /evolve self-improves via memory, **/update ingests external truth** — the third foundational write-loop for ritsu-works AI-native operations.

### Success criteria

- [ ] **SC1** ≥10 successful `/update` runs by 2026-06-30 (`ops.agent_runs WHERE agent_slug='update' AND state='completed'`)
- [ ] **SC2** ≥80% non-revert rate, 30-day rolling window by 2026-07-01
- [ ] **SC3** ≥5 borderline extractions reviewed via `/update review` by 2026-06-30 (verify gate exercised)
- [ ] **SC4** ≥1 K4 revert observed by day-30 (safety net engages)
- [ ] **SC5** Monthly cost ≤ $30 in `ai-ops-entity-update` bucket
- [ ] **SC6** `pnpm check` passes after every completed /update (drift prevention)

### Out of scope (v1.0)

- hook entity type (D-Std safety; defer v1.1)
- pillar / folder / workflow entity types (semantic gaps; defer v1.1-v1.2)
- mass-update / cross-entity transactional / webhook-driven (v1.2-v2.0)
- outside-voice auto-call (defer v1.1)

## 2. Domain Analysis Summary

`/update` is internal infrastructure for an AI-native operating system, not a customer-facing product. Domain: **code** (max-hit 26 keywords). Routed to `@cto`; independence satisfied via prior codex outside voice in /plan-eng-review (10 findings, all resolved in v3.0 architecture).

The capability fills a gap in the AI-native ops landscape: tools like Cursor / Aider / Continue.dev / Devin solve "refs → file refresh" generically but lack (a) citation spine, (b) 3-bucket confidence + founder review, (c) K4 quality ratchet with mode-aware slack. This combination is novel as of 2026-05.

Within ritsu-works, /update positions between hand-edit (too informal) and /cla extend (too heavy):

| Mechanism | When founder picks it | Cost | Discipline |
|-----------|-----------------------|------|------------|
| Hand-edit | Sub-10-LOC tweaks | Free | None |
| `/update` | Mid-weight refs-driven refresh | ~$0.70/run | Citation + K4 + audit |
| `/cla extend` | Structural change (>100 LOC) | $1.50-3 | Full ceremony |
| `/evolve` | Self-improvement (no refs) | ~$0.50/run | K4 strict |

### Industry benchmarks

| Pattern | Industry typical | Our target |
|---------|------------------|------------|
| Cost per ref-driven refresh | $0 (free hand-edit) or $1+ (Cursor session) | $0.50-1.00 |
| Time per refresh | 5-30 min hand-edit | 2-5 min /update + review |

## 3. Selected Option (Option A — v3.0 separate-commands + shared-infrastructure)

**Architecture:** Two distinct slash commands (`/update` and `/evolve`) expose distinct intents to founder, while sharing 100% of underlying infrastructure (universal entity-edit lock, shared `eval-evo/` skill suite, ops.agent_runs with `agent_slug` distinguishing).

### Why this option

- **Founder mental model wins.** "Evolve" = self-improvement (intrinsic); "Update" = refresh from external info (extrinsic). Two verbs match two intents.
- **No deadlock risk.** Universal lock (Sprint 1) eliminates cross-system collisions between /update + /evolve + /cla extend.
- **Convention fit.** ritsu-works has 16+ commands following one-verb-per-intent. Adding `/update` is symmetric; hiding behind `/evolve --refs` would break convention.
- **Future divergence supported.** /update will grow webhook-driven (v2.0), mass-update (v1.2), cross-entity (v1.2); /evolve won't. Separate commands avoid flag overload.
- **Zero code duplication.** Both orchestrators thin façades over shared skills.

### Trade-offs accepted

- ~$3-5 extra build cost vs v2.0 merge (acceptable — lifetime UX win compounds)
- 2x command files to maintain (acceptable — orchestrators are thin)
- Founder must understand 2-verb mental model (acceptable — decision matrix in §10)
