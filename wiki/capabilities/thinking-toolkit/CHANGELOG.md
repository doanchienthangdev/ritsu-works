## v3.7.0 — 2026-06-08 — the CONSULT checkpoint: convene a `/muse` MASTER as a McKinsey team member

**`/cla extend` (autonomous, founder asleep)** · the founder's ask: *"In a `/think mckinsey` run there are points that need the expertise/principles of the legends in `/muse`. Integrate a `/muse` exchange from some checkpoint: at that checkpoint McKinsey frames the problem, identifies + calls an expert X via `/muse:X`, then runs an interactive exchange with that expert (with the option for me to join OR be skipped), self-selects an approach with `/muse:ogilvy` (or lets me interact), takes the result back, and continues — natural, like inviting a master to collaborate. E.g. a landing-page-rewrite problem could invite David Ogilvy."* Proposal: `.archives/cla/mckinsey-muse-consult/`.

**The insight:** the engine's data sweep answers *"what is TRUE?"* (deepask / wiki / gbrain / supabase / deep-research). It had no first-class way to ask *"what would a MASTER do here, and why?"* — a **craft / domain-mastery JUDGMENT** (copy that sells, positioning, pricing psychology, a first-principles teardown). `/muse` has 29 installed legends (incl. **david-ogilvy** ✓, kotler, schwartz, munger, voss, graham, rams) but lived entirely outside the engine. v3.7 bridges them.

- **NEW 8th team session `kind: consult`** + **NEW skill `thinking-toolkit/mckinsey-consult`** (the checkpoint playbook). At a checkpoint where the live sub-need is a craft judgment that survived knock-out — *not* a fact (→ a data tool) and *not* analytical structure (→ a `/think` micro-framework) — the engine **FRAMEs** the need → **SELECTs** the legend (muse:who 0-80 fit reasoning, or `--consult=<persona>`) → **runs the exchange** → **VALIDATEs** → **RECORDs** → continues.
- **Two participation seats (the founder's "tham gia hoặc bỏ qua tôi").** `--consult=founder` (default when `--mode=interactive`) hands the client seat to the founder — a real `/muse:<persona>` session. `--consult=auto` (default when `--mode=auto`) the engine **self-plays** the client seat from the run context (problem-statement + one-day-answer + analysis-log + the sub-need): the persona drives the cognitive MOVES, the engine answers from the problem-TRUTH (never a flattering guess; a question only the founder can answer is an `ask-user` receipt or an explicit assumption). Either way the consult is **announced** so a present founder can join or skip.
- **EVIDENCE-NOT-DECIDER (the load-bearing discipline).** A legend's recommendation is **degree-6/7 expert judgment**, run through the validation gate like any datum: knock-out · triangulate vs the pulled data (coheres → double down; conflicts → resolve *with the founder*, not by deferring to the celebrity) · honesty-label. *"Ogilvy said so"* never launders past the gate; the synthesize→recommend call stays with the engine (Sell) + the founder. Same shape as the deepask `evidence-not-decider` guard.
- **NEW 11th run artifact `consult-log.md`** (the expert-consultation ledger: id `E<n>` · checkpoint · persona(s) · sub-need · participation · recommendation · `~/.muse` session-ref · degree · gate-verdict) + the **`[E<n>]` consult-receipt gate** in `mckinsey-run.cjs` — every analysis-log `muse-consult (<persona>) [E<n>]` datum must resolve to a consult-log row (mirror of the v1.8 HITL `[H<n>]` gate; discipline-not-proof; OPTIONAL — fires only when a consult is claimed). A consult also writes a `checkpoint-log` row (`kind: consult`) + a `toolkit-log` row (the legend as the SELECTED tool) + the `analysis-log` datum. `muse-consult` is excluded from the "real data pulled" check (a consult is judgment, never a substitute for a pull).

**Changed:** NEW `thinking-toolkit/mckinsey-consult/SKILL.md` · `mckinsey-run.cjs` (+`consult-log` ARTIFACT + TEMPLATE + the `[E<n>]` gate + the muse-consult data-pull exclusion) · `validate-mckinsey-workflow.cjs` (`ARTIFACTS` set-equal +`consult-log`; `TOOLS` +`muse-consult`) · schema `produces` enum (+`consult-log`) · `mckinsey-workflow.yaml` (**3.5.0 → 3.6.0**; +`muse-consult` `data_routing` row + `consult-log` artifact + `consult` on the `checkpoint-log` kind enum + `solve.produces`/`solve.skills` + a top-level `consult` engine section) · `mckinsey-workflow/SKILL.md` (the 8th session + the `--consult` flag + §CONSULT + the routing row + 11-artifact references + a `/muse` composition bullet) · `think.md` (the mckinsey row + `--consult` + the in-engine `/muse` composition note). **`/muse` is a SYSTEM-level skill** (`~/.claude/skills/muse/`) — invoked read-only, **never modified**; the integration lives entirely in the mckinsey engine.

**Tests:** +1 `describe` (`CONSULT receipt gate`) in `mckinsey-run.test.ts` — 13 cases mirroring the HITL gate suite (matched / missing-tag / dangling / phantom-`<E1>` / optional / non-consult-untouched / one-way / case-insensitive / multi-tag / decoy-cell / independent-from-hitl / not-real-data-pull). `mckinsey-workflow.test.ts` auto-covers `muse-consult` via its `for (const t of TOOLS)` loop + the real-catalog conformance test. **252 mckinsey-suite tests green** (run-folder 173 + hook/coherence/tier1/trace 79). **No new DB table, no migration, no new `/think` verb.** `thinking-toolkit` → **v3.7.0**. ## v3.6.0 — 2026-06-06 — Per-checkpoint tool-selection + a deeper reasoning-trace

**`/cla extend` (autonomous, founder away)** · the founder's probe after v3.5: *"Quá trình thực hiện mckinsey 4S gồm nhiều bước — có lựa chọn toolkit thực sự tại MỖI checkpoint không?"* Honest answer (checked against the code): **no** — v3.5 keyed the ledger by 4S step (4), the gate required ≥1 for the whole run, and the demo ledger was reconstructed post-hoc. The founder's directive: tool-selection must be **real at each step** (the McKinsey execution model — *"1 kho công cụ + 1 workflow nghiêm ngặt; tại mỗi bước: dựa trên thông-tin-đã-có + pool → chọn toolkit phù hợp → tư duy + thu thập → tiến"*), **logged + presented per-checkpoint**, and the reasoning-trace must **explain the tool choice in each step** and be **far deeper / more insightful** (the last one was *"sơ sài"*). Proposal: `.archives/cla/per-checkpoint-toolkit-selection/proposal.md`.

- **Bind tool-selection to the checkpoint structure.** `toolkit-log.md` gains a **`checkpoint`** column (the C-id from `checkpoint-log`) — every selection is anchored to the team-session where it happened. The artifact SET is unchanged (still 10 — only a column added).
- **The gate now enforces per-step selection.** `--before-sell`: **ERROR** if any 4S stage that ran a checkpoint recorded NO tool-selection (*"không để đấy"* — you can't run the Solve sessions and select no Solve tools); **WARN** on any individual checkpoint with no selection bound to it (a pure-proceed porpoise may legitimately reuse a prior tool). Keeps the ≥1-total ERROR + the no-rejected WARN.
- **The McKinsey execution loop, documented.** `mckinsey-workflow/SKILL.md` makes per-checkpoint tool-selection a formal step: at EACH checkpoint — **READ** info-so-far → **CLASSIFY** → **LOAD** `thinking-tool-index/<step>.md` → **SELECT ≤3** → **APPLY** (think + gather) → **RECORD** (bound to the C-id) → **PROCEED** — plus a "which tools tend to fit which checkpoint" starting map. A `record` stage updated to per-checkpoint; `mckinsey-workflow.yaml` → 3.5.0.
- **The trace shows the binding + goes DEEPER.** `trace-extract.cjs` joins each selection to its checkpoint kind; `trace-build.py`'s `toolkit_map` shows `STAGE · C-id kind` badges, sorted by checkpoint order (you watch the tool-choices happen in sequence). The `reasoning-trace` SKILL raises the **depth bar**: a **6-beat rhythm** with an explicit **tool-choice beat** (which tool at this checkpoint, classified how, why this / why-not that — sourced from the ledger) + a **what-it-revealed insight beat**; each milestone is 3–6 developed paragraphs (explain-don't-assert · draw-out-the-insight · connect-the-dots), not a thin skeleton.

**Demonstration:** the 100-love-paying trace rewritten to the deeper bar; its `toolkit-log` rebound to the real checkpoints (C1 frame → C7 pre-wire) — the per-checkpoint gate passes (every stage + every checkpoint covered), and the `toolkit_map` now reads down C1→C7 with each tool-choice in sequence. **Tests:** the toolkit-gate suite reworked to per-checkpoint (per-stage ERROR + per-checkpoint WARN + the all-stages/rejected paths); the trace-extract checkpoint-binding test (joins the kind). **Honest scope:** the gate is still discipline-not-proof (it checks each stage *recorded* a checkpoint-bound selection, not that the reasoning was optimal); the demo ledger is bound to the real checkpoints but authored now — what makes future runs genuinely per-checkpoint-live is the SKILL loop + the per-stage gate. `thinking-toolkit` → **v3.6.0**. Run record: `.archives/cla/per-checkpoint-toolkit-selection/`.
