# Model Ritsu Feature Prioritisation as an Issue Tree, Not a Hypothesis Pyramid

**Type:** idea · **From:** *Cracked It! How to Solve Big Problems and Sell Solutions Like Top Strategy Consultants* (Bernard Garrette, Corey Phelps, Olivier Sibony, 2018), Ch 5 — Structure the Problem: Pyramids and Trees

## Summary

Ritsu's product team often starts from a candidate feature hypothesis (e.g., 'we should add spaced repetition'). Applying the chapter's logic suggests that running an open issue tree — 'what learning-outcome improvements are achievable for which user segment at what cost?' — before committing to a feature hypothesis would surface better options and avoid confirmation bias in backlog prioritisation. This maps to /cla Phase 2 and SOP-PRODUCT-004.

## Ritsu relevance

The chapter's warning that hypothesis-driven structuring 'encourages a narrow definition of the problem' applies directly to product feature selection at Ritsu: starting with a feature hypothesis risks locking out superior alternatives before the problem space is fully explored.
