# Issue Tree (MECE Decomposition)

*Category: problem-solving · Toolkit: Leadership Development*

## What it is
A hierarchical visual map that breaks a complex problem into exhaustive, non-overlapping branches — each a testable sub-question — until the problem is fully decomposed into analysable components.

**Origin:** Developed and refined at McKinsey & Company throughout the 1970s–1980s. Barbara Minto codified the underlying MECE (Mutually Exclusive, Collectively Exhaustive) principle in 'The Pyramid Principle' (1987). The issue tree is the standard McKinsey problem-structuring tool taught to all new analysts.

## Why it works
Complex problems cannot be solved by intuition alone. An issue tree makes the structure of a problem visible and testable: if every branch is MECE, then any finding from any branch either confirms or eliminates the overall hypothesis. This prevents analysts from missing entire categories of root cause (the 'CE' — collectively exhaustive test) and from double-counting effort (the 'ME' — mutually exclusive test).

## When to use
Immediately after the SMART problem statement is agreed. Use whenever a problem has multiple possible root causes or multiple dimensions. Essential for any problem that will take more than 2 days to solve.

## Visual
`tree`

## Step-by-step tutorial
1. Write the overarching problem question at the top of a blank page or whiteboard: e.g., 'Why has our market share declined 5pp in 12 months?'
2. Identify the 2–4 mutually exclusive Level-1 branches that together cover all possible explanations. For a profit problem, the canonical Level-1 split is Revenue vs. Cost. For a market share problem, it might be 'Did we lose customers?' vs. 'Did we fail to win new customers?' vs. 'Did the overall market shrink?'
3. Test MECE at each level: (a) Do any two branches overlap? If yes, merge or redefine. (b) If all branches resolved favourably, would the problem definitely be solved? If no, you have a gap — add a branch.
4. Drill down to Level 2 and Level 3 on each branch until you reach a sub-issue that can be answered with a single analysis or data pull.
5. Convert each leaf node into a hypothesis: 'We have lost market share because [specific branch].' This is the testable unit your work plan will address.
6. Prioritise branches using the 2x2 impact/solvability matrix before planning analyses — not every branch needs equal investigation.

## Real-life example — McKinsey & Company engagement for a European retail bank (composite, anonymised case study published in McKinsey Quarterly 2019)
A retail bank saw NPS fall from +35 to +12 over 18 months. The team built an issue tree: Level 1 — Is it a product issue or a service issue? Level 2 (product) — Is it pricing? Features? Availability? Level 2 (service) — Is it in-branch? Digital? Call centre? The MECE analysis quickly isolated the problem: digital banking NPS was +50 (excellent) while call centre NPS was -15 (driving the overall decline). The root cause was staffing and training in the call centre, not the product — saving the bank from an expensive product redesign.

**So what:** An issue tree prevents 'solution-first' thinking by forcing the team to explore all plausible root causes before committing analytical effort. The 15-minute exercise of building the tree often surfaces the answer more reliably than weeks of data analysis.

## Template
Draw the tree top-down. At each level, write the question each branch answers. Test MECE at each level before proceeding. Stop when each leaf node can be answered with one data source or one analysis.

- [ ] Leaf nodes (testable hypotheses): List each leaf as 'The problem is caused by ___' — these become your work plan items.

## Pitfalls
- Hypothesis-free issue trees: Building a 'hypothesis-free' tree that lists every conceivable sub-issue wastes time. Always attach a directional hypothesis to each branch from the outset — this is what 'hypothesis-driven' means in consulting practice.
- Failing the MECE test: The most common failure is having overlapping branches (e.g., 'sales declined' and 'revenue declined' at the same level — these are the same thing). Before proceeding, always ask: 'If Branch A is confirmed, does that tell us anything about Branch B?' If yes, they overlap.
- Going too deep too fast: Analysts often drill to Level 4 before validating Level 1. Build the tree one level at a time and validate each level before drilling further.
