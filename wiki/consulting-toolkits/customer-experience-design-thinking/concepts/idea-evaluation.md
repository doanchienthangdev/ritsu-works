# Idea Evaluation Canvas

*Category: ideation · Toolkit: Customer Experience Strategy & Design Thinking*

## What it is
A structured one-page canvas that captures the essential elements of a selected idea — description, target user, key assumption, expected benefit, and key risk — creating a consistent record for each idea advancing to prototyping and establishing the testable hypothesis for the Prototype phase.

**Origin:** Synthesized from the Lean Canvas (Ash Maurya, 2012), the Value Proposition Canvas (Osterwalder, 2014), and IDEO's 'Concept brief' format.

## Why it works
Ideas selected from an ideation session often exist only as a sticky note. Without a structured record, the team's understanding of the idea diverges during prototyping. The Idea Evaluation Canvas forces explicit documentation of the idea's core components — especially the key assumption and key risk, which define the testing agenda for the Prototype phase.

## When to use
Use at the end of Phase 7 (Ideate) for every idea that scores ≥12/20 on NABC and advances to prototyping. The canvas becomes the brief for the Prototype phase.

## Step-by-step tutorial
1. 1. Complete one canvas per idea that survives dot voting in the Ideation Workshop.
2. 2. Write the 2-sentence description: what is the idea, and how does it work for the user?
3. 3. Name the Target Persona: which specific persona from the research phase does this idea serve?
4. 4. Identify the Key Assumption: the one belief about user behavior, technology, or business economics that, if wrong, would invalidate this idea entirely.
5. 5. Quantify the Expected Benefit: which KPI does this idea move, and by how much? (Use the Define Success Statement as the target.)
6. 6. Identify the Key Risk: the most likely reason this idea fails to achieve the expected benefit.
7. 7. Enter the NABC score from the evaluation panel.
8. 8. Record the decision: Prototype (advance), Park (hold for review if top ideas fail), or Discard.

## Real-life example — PayPal
PayPal's design team used Idea Evaluation Canvases during a redesign of the payment confirmation experience. One canvas read: 'Idea: Real-time payment status animation. Target: Maria (first-time buyer, 28, mobile-first). Key assumption: users who see visual confirmation of payment processing will have lower anxiety and fewer support contacts. Expected benefit: payment-related support tickets -30%. Key risk: animation timing diverges from actual processing time, creating false confidence.' This canvas framed the prototype test precisely — 5 users tested with and without the animation — and defined the success criterion before the prototype was built.

**So what:** The Key Assumption is the hypothesis the prototype must test — making it explicit before prototyping prevents the team from building a test that doesn't answer the right question.

## Template
Complete one canvas per idea advancing to prototyping. Every field must be completed — 'unknown' is an acceptable answer for Expected Benefit if truly unknown, but triggers a research requirement.

- [ ] Idea title: ___
- [ ] 2-sentence description: ___
- [ ] Target persona: ___
- [ ] Key assumption (must be true for the idea to work): ___
- [ ] Expected benefit (specific KPI + magnitude): ___
- [ ] Key risk (most likely failure mode): ___
- [ ] NABC total score: ___/20
- [ ] Decision: PROTOTYPE / PARK / DISCARD
- [ ] Prototype type planned (lo-fi sketch / storyboard / hi-fi / PoC): ___
- [ ] Canvas completed by: ___ Date: ___

## Pitfalls
- Vague key assumptions: 'users will like this feature' is not a testable assumption. Counter: the Key Assumption must be specific enough to be falsified by a prototype test — 'users who see the confirmation animation will reduce repeated payment submissions from 15% to < 5%.'
- Skipping the canvas for 'obvious' ideas: teams skip canvas completion for ideas they are confident will work. Counter: the canvas is mandatory for every idea advancing to prototyping — confidence is not a substitute for documentation.
