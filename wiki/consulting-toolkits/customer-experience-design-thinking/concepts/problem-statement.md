# Problem Statement

*Category: planning · Toolkit: Customer Experience Strategy & Design Thinking*

## What it is
A precisely crafted, single-sentence (or short-paragraph) formulation of the core design challenge that frames the problem from the user's perspective, encodes the root cause as context, and defines a measurable success criterion — giving the ideation team a focused brief that invites creative solutions without prescribing them.

**Origin:** Formalized in design thinking practice by the Stanford d.school and IDEO; draws on the tradition of 'design briefs' from product design and the 'problem framing' discipline from McKinsey consulting.

## Why it works
A well-framed problem is half-solved. The Problem Statement prevents two failure modes: (1) solving a symptom (fixing the broken button) when the root cause is systemic (no one owns the checkout experience), and (2) framing the problem as a solution ('We need a new app') which forecloses creative alternatives. The format '[User] needs [X] because [insight], but today [barrier]. We'll know we've solved it when [measurable outcome]' forces the team to encode the user, the root cause, the barrier, and the success criterion simultaneously.

## When to use
Use at the end of the Define phase, after Five Whys and root-cause analysis are complete. It is the single output that bridges Define and Ideate — no ideation session should begin without a signed Problem Statement.

## Step-by-step tutorial
1. 1. Start from the root cause identified in the Five Whys analysis for the highest-priority pain point.
2. 2. Draft the Problem Statement using the template: '[User/segment] needs [a way to do X] because [the insight/root cause from research], but today [the current barrier]. We will know we have solved this when [measurable success criterion].'
3. 3. Check the statement against three criteria: (a) Does it describe a problem, not a solution? (b) Does it encode the user's perspective, not the company's? (c) Is the success criterion measurable?
4. 4. Run the Card Sort test: write the Problem Statement on 10 identical cards. Give one to each of 10 team members. Ask them to sort it as 'clearly solvable', 'too broad', or 'too narrow'. Target: ≥80% 'clearly solvable'.
5. 5. If the Card Sort fails (< 80% clearly solvable): 'too broad' means split the problem into sub-problems and address the highest-priority one; 'too narrow' means the constraint in the statement is too specific — loosen it.
6. 6. Get the sponsor to sign the Problem Statement card. This creates accountability and prevents scope drift.
7. 7. Post the signed Problem Statement visibly in the team workspace and refer to it explicitly at the start of every ideation and design session.

## Real-life example — Bank of America
Bank of America's design team (working with IDEO) applied the Problem Statement methodology when addressing low enrollment in savings programs. Their initial (bad) Problem Statement was: 'We need a new savings product.' Revised using the template: 'Young adults (25–35) who have discretionary income need a way to save money consistently because they lack the financial discipline and habit formation to save manually, and today's bank transfer process feels effortful and deprivation-like. We'll know we've solved it when automatic savings enrollment among this segment increases by 30%.' This statement led to the 'Keep the Change' program (round up debit purchases to the nearest dollar, transfer the difference to savings) — a solution that required no new financial product, just a behavioral design insight hidden in the problem framing.

**So what:** The Problem Statement determines the solution space. A narrow, well-framed problem statement unlocks solutions that a broad statement misses.

## Template
Use this template to draft and validate your Problem Statement. Require evidence for the 'because' clause from user research.

- [ ] User/segment: ___
- [ ] Need ('a way to...'): ___
- [ ] Because (root cause from research): ___
- [ ] But today (the current barrier): ___
- [ ] Success criterion (measurable): ___
- [ ] Full statement: '[___] needs [___] because [___], but today [___]. We will know we've solved this when [___].'
- [ ] Card Sort result: ___% clearly solvable (target ≥80%)
- [ ] Adjustment made (if < 80%): ___
- [ ] Sponsor signature: ___ Date: ___

## Pitfalls
- Solution masquerading as a problem: 'We need to build a chatbot to reduce call volume' is a solution, not a problem statement. Counter: any problem statement that contains a technology, feature, or channel name is actually a solution — rephrase to describe the user's experience.
- Skipping the Card Sort: teams write a problem statement, nod, and proceed to ideation without validating it. Counter: the Card Sort is a 20-minute exercise that costs nothing and prevents weeks of wasted ideation on the wrong problem.
- Changing the Problem Statement mid-ideation: teams frequently drift from the agreed problem statement when ideation gets difficult. Counter: post the signed statement on the wall and start each session by reading it aloud.
