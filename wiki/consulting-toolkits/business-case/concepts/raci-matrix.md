# RACI Matrix

*Category: planning · Toolkit: Business Case*

## What it is
A responsibility-assignment matrix that maps every project deliverable to four roles: Responsible (does the work), Accountable (owns the outcome), Consulted (provides input before decisions), and Informed (receives updates after decisions).

**Origin:** A standard project management tool formalised in the PMI PMBOK and widely attributed to consulting practice in the 1970s–80s. PMI PMBOK 7th Edition (2021) defines the RACI as part of project governance.

## Why it works
Unambiguous accountability is the single most reliable predictor of whether a deliverable gets produced. The RACI eliminates the two most common project failures: diffused accountability (multiple Accountables = no one accountable) and communication overload (everyone consulted on everything). By making accountability explicit and visible, it converts informal expectations into formal commitments.

## When to use
At the end of Step 1.3 (Scope and Team definition) — before any work begins. Revisit when scope changes significantly.

## Step-by-step tutorial
1. List every deliverable in the project in rows.
2. List every stakeholder role in columns (not individuals — roles, so the matrix survives personnel changes).
3. Assign R (Responsible) to the role that does the work — there may be multiple Rs.
4. Assign A (Accountable) to exactly one role per deliverable — the person who owns the outcome and is answerable to the board. Never two As for the same deliverable.
5. Assign C (Consulted) to roles that must provide input before the deliverable is finalised — two-way communication.
6. Assign I (Informed) to roles that receive updates after decisions — one-way communication.
7. Review with every role for gaps and conflicts: 'Do you agree you own this?' and 'Are there any deliverables you should be consulted on but are not?' Fix disagreements before the project starts.

## Real-life example — Airbnb (market expansion to Japan, 2014)
When Airbnb expanded into Japan, the RACI was critical: the VP Japan was Accountable for market revenue targets but Responsible only for market strategy; local BD leads were Responsible for host acquisition; legal was Consulted on regulatory compliance per listing type; global finance was Informed on quarterly actuals. The clarity prevented the classic consulting failure where two senior people each thought the other owned the regulatory risk — a mistake that caused a 6-month setback for a competitor entering the same market.

**So what:** A RACI completed before the project starts converts implicit expectations into explicit, auditable commitments — and prevents the most common accountability failure.

## Template
List every project deliverable in rows. List every stakeholder role (not names) in columns. Fill each cell with R, A, C, I, or blank. Every row must have exactly one A. Validate: no row has two As; no role has only Is (over-informed); no column is blank for a key stakeholder.

- [ ] Deliverable: [Name of deliverable or decision]
- [ ] [Role 1]: [R / A / C / I / blank]
- [ ] [Role 2]: [R / A / C / I / blank]
- [ ] [Role 3]: [R / A / C / I / blank]
- [ ] Validation check: Does this row have exactly one A? Does the A-holder agree they own this outcome?

## Pitfalls
- Two Accountables for the same deliverable — fix: force the discussion about who owns it before the project starts; a deliverable with two Accountables effectively has none.
- Assigning everyone C — consultation overload destroys decision speed. C means genuine two-way input is needed before finalisation; use I for 'keep them in the loop.'
- Role-level vs individual-level — always assign to roles (not names) so the matrix survives personnel changes.
