# Problem Framer (CLA Phase 1)

## Khi nào sử dụng

- Được gọi bởi `.claude/commands/cla.md` sau khi Phase 0 thành công, với capability folder + row `ops.capability_runs` đã được tạo.
- `ops.capability_runs.current_phase = 1`, `state = 'proposed'`.

## Đầu vào

- `capability_id` — slug, set bởi Phase 0.
- `raw_proposal` — văn bản mô tả vấn đề gốc của founder.
- `triggered_by` — `cla_command` (v1.0). Tương lai: `voice_note`, `wiki_entry`.
- `refs_dir` — tùy chọn `.archives/cla/<capability_id>/refs/` nếu founder truyền file-path `--refs`.
- `wiki_refs_dir` — tùy chọn `runtime/cla/refs/<capability_id>/` (v1.1) nếu founder truyền `--refs=wiki:src=<spec>` hoặc `--refs=wiki:query="<text>"`. Files ở đây là các bundle được sinh ra bởi `/wiki get` trong Phase 0; mang header annotation chỉ ra chúng đến từ source spec hoặc query nào. Coi như primary input context — founder đã chủ động curate kiến thức này.

## Quy trình

### Bước 1 — Tiếp nhận tài liệu tham chiếu (tùy chọn)

Hai folder ref có thể tồn tại (v1.1):
- `.archives/cla/<capability_id>/refs/` — files được copy từ args `--refs <file-path>`
- `runtime/cla/refs/<capability_id>/` — wiki bundles được sinh ra bởi `/wiki get` từ args `--refs=wiki:src=` / `--refs=wiki:query=`

Cho mỗi folder:
- Liệt kê files.
- Đọc từng file (cap ở 5 files, 50 KB mỗi file — vượt quá, tóm tắt phần còn lại chỉ là filenames).
- Cho các files trong `runtime/cla/refs/`: header mang annotation `**Query:**` hoặc `**Source spec:**`; surface điều này như "founder-curated knowledge from wiki" trong context excerpts để báo hiệu intent rõ ràng vs ad-hoc file dump.
- Xây dựng một section "context excerpts" ngắn (≤ 800 tokens) sẽ được embed vào LLM prompt cho các bước 2-4.
- Nếu một ref trông giống như `problem.md` hoặc `spec.md` của một capability đang tồn tại, surface đó như một duplicate-or-extension hint cho bước 5.

### Bước 2 — Tinh chỉnh phát biểu vấn đề

Từ `raw_proposal` (+ refs context tùy chọn), tạo một đoạn văn duy nhất, súc tích theo dạng:

> \{verb} \{object} \{quantity or quality target} \{time horizon} \{constraint, if any}

Ví dụ:
- "Acquire 10 new paying customers per day, sustained over a rolling 30-day window, with CAC under $20."
- "Auto-triage support tickets from Telegram into FAQ-handled vs founder-required within 5 minutes of arrival."

Phát biểu đã tinh chỉnh nên ≤ 50 từ, chứa ít nhất một measurable target, và tránh các từ chung chung ("scale", "improve", "automate stuff").

### Bước 3 — Tạo 5-7 câu hỏi làm rõ

Mỗi câu hỏi bao quát một trong các chiều dưới đây; chọn cái nào thực sự còn mơ hồ. Bỏ qua các chiều rõ ràng từ raw proposal.

| # | Chiều | Mẫu câu hỏi |
|---|---|---|
| 1 | Đối tượng | "Who is the target user/customer/persona?" |
| 2 | Định nghĩa | "When you say '\{key noun}', do you mean \{option A} / \{option B} / \{option C}?" |
| 3 | Volume | "Is the \{target} a floor (sustained) or a peak (one-off)?" |
| 4 | Budget | "What's the spend ceiling (setup + monthly)?" |
| 5 | Time horizon | "By when do you want this in production?" |
| 6 | Constraints | "Anything off-limits — channels, ethical lines, founder bandwidth, dependencies?" |
| 7 | Existing fit | "Which pillar does this live in? Is it net-new or an extension of an existing capability?" |

Format mỗi câu hỏi cho `AskUserQuestion`:

```jsonc
{
  "question": "When you say 'customer', do you mean ...",
  "header": "Customer def",
  "multiSelect": false,
  "options": [
    { "label": "Signed up", "description": "..." },
    { "label": "Activated (first quiz)", "description": "..." },
    { "label": "Paid", "description": "..." }
  ]
}
```

Gom các câu hỏi vào batches ≤ 4 mỗi `AskUserQuestion` call (Anthropic limit). Orchestrator command sẽ phát hành call(s); skill này tạo question payloads.

### Bước 4 — Soạn thảo tiêu chí thành công

Format mỗi criterion như:

> \{observation} happens, measured by \{table/path/KPI}, target \{value}, by \{date}

Surface ≥ 2 criteria. Mỗi cái PHẢI đo lường được từ `ops.kpi_snapshots` hoặc `metrics.*` (không phát minh KPIs không tồn tại — nếu cần KPI mới, flag là "NEW: needs registration in Phase 5").

### Bước 5 — Nêu rõ các giả định + kiểm tra trùng lặp

- Liệt kê 3-7 giả định, mỗi cái bắt đầu bằng "ASSUMING ...".
- Chạy slug-collision check: đọc `knowledge/capability-registry.yaml`; nếu slug hoặc một slug tương tự tồn tại, surface: "Existing capability `<slug>` is in state `<state>`. Extension or independent?"

### Bước 6 — Viết `.archives/cla/<capability_id>/problem.md`

### Bước 8 — Trả về cho orchestrator

Orchestrator (`.claude/commands/cla.md`) tiếp quản:
- Phát hành các `AskUserQuestion` batches được xây dựng trong Bước 3.
- Gập câu trả lời của founder trở lại vào `problem.md` dưới mỗi dòng `**Founder answer:**`.
- Nếu founder trả lời `skip` cho mỗi câu hỏi, danh sách assumptions LÀ tập câu trả lời — note điều đó rõ ràng trong problem.md.

## Mode awareness (v1.1 — `cla-update-mechanism`)

Skill này được gọi bởi `/cla propose` (mode=`create`, the v1.0 path) VÀ bởi tất cả 5 update sub-flows (`/cla fix/extend/revise/tune/deprecate`). Orchestrator truyền `mode` qua `state_payload.update_mode` tại Phase 0; skill này đọc nó và điều chỉnh Process của mình.

| Mode | Hành vi Skill |
|---|---|
| `create` (default) | Full Process Steps 1-8 ở trên. Tạo 5-7 câu hỏi làm rõ. Output: `.archives/cla/<id>/problem.md` |
| `fix` | Bỏ qua Steps 1, 3, 5 (no slug gen, no clarifying questions, no assumptions). Đọc existing `wiki/capabilities/<id>/problem.md` + `spec.md`. Tạo focused `fix-description.md` với: what's broken, root cause hypothesis, fix scope. ABORT nếu scope dường như cần spec change. Output: `.archives/cla/<id>-fix-<session_id>/fix-description.md` |
| `extend` | Bỏ qua Step 5 assumption surfacing (carry from existing). Tạo 3-5 câu hỏi làm rõ CHỈ về extension delta (không phải full re-framing). Output: `.archives/cla/<id>-extend-<session_id>/extension-description.md` |
| `revise` | Đọc existing problem.md + spec.md. Tạo 5-7 câu hỏi làm rõ specific cho architecture concerns ("what fundamentally changes? what's preserved? minimum viable revision?"). Output: `.archives/cla/<id>-revise-<session_id>/revision-problem.md` |
| `tune` | Parse founder description vào structured `tune-spec.md`: which KPI(s), old value(s), new value(s), reason. KHÔNG có câu hỏi làm rõ (tune đủ nhỏ để fit trong 1 description). Output: `.archives/cla/<id>-tune-<session_id>/tune-spec.md` |
| `deprecate` | Capture deprecation rationale: why now, migration path for users, data handling. Single output `deprecation-rationale.md` trở thành phần của retrospective. KHÔNG có câu hỏi làm rõ (rationale ngắn). Output: `.archives/cla/<id>-deprecate-<session_id>/deprecation-rationale.md` |

**Common across modes:** Phase 0 lock acquisition + lineage row INSERT xảy ra TRƯỚC khi skill này chạy (trong orchestrator). Skill này giả định row tồn tại với `state_payload.update_mode` set.
