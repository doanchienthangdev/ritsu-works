# Monthly Learning Review

> Quarterly cadence quá chậm; weekly quá thường xuyên cho công ty 1 founder. Monthly là sweet spot.

Kỹ năng này đóng vòng lặp trong Strategy E. Suốt tháng, agent gửi run summaries và founder ghi lại các sửa chữa. Vào cuối tháng, kỹ năng này tổng hợp và hiển thị những gì đáng trở thành canonical.

## Khi nào dùng

**Scheduled:** ngày 1 của mỗi tháng lúc 09:00 ICT (giờ Việt Nam), qua workflow runner. Cấu hình trong `workflows/monthly-learning-review.yaml` (được tạo ở Phase F).

**Manual:** founder có thể gọi qua `/run-monthly-review` để review ad-hoc (ví dụ: sau một incident lớn).

KHÔNG dùng:
- Thường xuyên hơn hàng tháng (tín hiệu quá noisy)
- Cho \< 4 tuần dữ liệu tích lũy (quá ít mẫu)
- Trong một incident đang diễn ra (hoãn lại cho đến sau — điều kiện ổn định quan trọng)

## Inputs

| Input | Type | Required | Description |
|---|---|---|---|
| `month` | string | no | YYYY-MM để review; mặc định là tháng lịch trước |
| `roles` | string[] | no | Các role để bao gồm; mặc định là tất cả non-founder roles |
| `min_pattern_count` | int | no | Số lần tối thiểu để hiện một mẫu; mặc định 3 |

## Outputs

| Output | Format | Destination |
|---|---|---|
| Patterns report | Markdown | `.archives/learning-reviews/<YYYY-MM>-patterns.md` |
| Telegram notification | Inline message | Telegram của founder |
| (optional) Per-pattern PR drafts | Branch + PR | GitHub, chỉ khi founder chọn "promote" |

## Procedure

### Bước 1 — Định nghĩa time window

Nếu `month` không được cung cấp: đặt thành tháng lịch trước (ví dụ: vào 2026-05-01, mặc định là 2026-04). Tính toán `start_ts` và `end_ts` boundaries.

### Bước 2 — Chạy các pattern queries

Sáu truy vấn lại `ops.*`. Mỗi cái hiển thị một loại mẫu khác nhau.

#### Query A — Recurring failures

```sql
SELECT
  agent_role,
  action_name,
  COUNT(*) AS failure_count,
  AVG(cost_usd) AS avg_cost,
  array_agg(DISTINCT id ORDER BY id) AS run_ids
FROM ops.agent_runs
WHERE completed_at BETWEEN $start AND $end
  AND outcome IN ('failed', 'rejected', 'aborted')
GROUP BY agent_role, action_name
HAVING COUNT(*) >= $min_pattern_count
ORDER BY failure_count DESC, avg_cost DESC
LIMIT 20;
```

Action items: mỗi hàng là một candidate "cái này thất bại quá thường xuyên, time for a skill/SOP refinement."

#### Query B — Recurring corrections

```sql
SELECT
  ar.agent_role,
  ar.action_name,
  COUNT(c.id) AS correction_count,
  array_agg(DISTINCT c.correction_note ORDER BY c.correction_note) AS unique_notes
FROM ops.corrections c
JOIN ops.agent_runs ar ON ar.id = c.run_id
WHERE c.ts BETWEEN $start AND $end
GROUP BY ar.agent_role, ar.action_name
HAVING COUNT(c.id) >= $min_pattern_count
ORDER BY correction_count DESC
LIMIT 20;
```

Action items: mỗi hàng nói "founder liên tục sửa cùng một điều — codify nó."

#### Query C — High-cost outliers

```sql
WITH per_action_stats AS (
  SELECT
    agent_role, action_name,
    AVG(cost_usd) AS mean_cost,
    STDDEV(cost_usd) AS stddev_cost,
    COUNT(*) AS n
  FROM ops.agent_runs
  WHERE completed_at BETWEEN $start AND $end
  GROUP BY agent_role, action_name
  HAVING COUNT(*) >= 5
)
SELECT
  ar.id, ar.agent_role, ar.action_name, ar.cost_usd,
  pas.mean_cost, ((ar.cost_usd - pas.mean_cost) / NULLIF(pas.stddev_cost, 0)) AS z_score
FROM ops.agent_runs ar
JOIN per_action_stats pas USING (agent_role, action_name)
WHERE ar.completed_at BETWEEN $start AND $end
  AND ar.cost_usd > pas.mean_cost + 2 * pas.stddev_cost
ORDER BY z_score DESC
LIMIT 10;
```

Action items: outliers có thể chỉ ra inefficiency trong skill design (quá nhiều lệnh gọi tool, retry loops).

#### Query D — Skills with declining outcomes

```sql
WITH skill_outcomes AS (
  SELECT
    action_name,
    DATE_TRUNC('week', completed_at) AS week,
    SUM(CASE WHEN outcome = 'success' THEN 1 ELSE 0 END)::float / COUNT(*) AS success_rate,
    COUNT(*) AS n
  FROM ops.agent_runs
  WHERE completed_at BETWEEN $start AND $end
  GROUP BY action_name, DATE_TRUNC('week', completed_at)
  HAVING COUNT(*) >= 3
)
SELECT action_name,
       jsonb_agg(jsonb_build_object('week', week, 'success_rate', success_rate, 'n', n)
                 ORDER BY week) AS weekly_trend
FROM skill_outcomes
GROUP BY action_name
HAVING COUNT(*) >= 3 -- ít nhất 3 tuần dữ liệu
ORDER BY action_name;
```

Trong post-processing, đánh dấu những action mà success_rate giảm > 15% trong tháng — có thể là skill regression.

#### Query E — Roles approaching budget caps

```sql
SELECT
  agent_role,
  SUM(cost_usd) AS month_spend,
  COUNT(*) AS run_count,
  AVG(tokens_used) AS avg_tokens
FROM ops.agent_runs
WHERE completed_at BETWEEN $start AND $end
GROUP BY agent_role
ORDER BY month_spend DESC;
```

So sánh với `budget.monthly_token_usd` của mỗi role từ `governance/ROLES.md`. Đánh dấu bất kỳ role > 80% cap — cần budget review hoặc skill optimization.

#### Query F — New action_names that emerged

```sql
SELECT
  action_name,
  array_agg(DISTINCT agent_role) AS roles_using,
  COUNT(*) AS first_month_runs,
  AVG(cost_usd) AS avg_cost
FROM ops.agent_runs
WHERE completed_at BETWEEN $start AND $end
  AND action_name NOT IN (
    SELECT DISTINCT action_name FROM ops.agent_runs
    WHERE completed_at < $start
  )
GROUP BY action_name;
```

Action items: các action mới có thể cần skill scaffolding. Kiểm tra xem mỗi action mới có matching SKILL.md không; nếu không, scaffold một cái.

### Bước 3 — Tổng hợp candidates

Đối với mỗi kết quả không trống, tạo một candidate entry:

```yaml

agent_role: ...
action_name: ...

  run_count: 7
  unique_correction_notes:
    - "..."
    - "..."
  trend: "+/- N% week-over-week"
  example_run_ids: [...]
proposed_change:
  type: <skill_update | charter_update | sop_creation | budget_adjustment | skill_scaffold>
  target_file: skills/blog-post-drafting/SKILL.md
  rationale: |
    Evidence-based reasoning ~3-5 sentences.
  draft_diff: |
    ## Bước 2 — Style verification
    + - Luôn bao gồm 1-2 internal links tới các trang Ritsu liên quan
    + - Từ chối bản soạn và re-prompt nếu không có internal link slots có sẵn

```

Priority rules:
- High: xuất hiện trong ≥ 2 loại query VÀ có founder corrections
- Medium: loại query duy nhất nhưng ≥ 5 occurrences
- Low: edge case đáng hiển thị nhưng có ít bằng chứng

## Tiêu chí chất lượng

Một run thành công:
- Hoàn thành trong \< 5 phút wall-clock
- Tạo ra từ 5 đến 30 candidates (quá ít = noise; quá nhiều = no signal)
- Mỗi candidate cite concrete run_ids như evidence
- High-priority candidates có complete `draft_diff`

## Chế độ lỗi

- **Insufficient data** — nếu total runs trong tháng \< 100, bỏ qua generation và report "insufficient data, deferring." Không tạo noise.
- **No new patterns** — nếu 0 candidates surface, tạo một brief "no significant patterns" report. Founder vẫn nhận được confirmation rằng review đã chạy.
- **Telegram delivery fails** — viết report file dù sao; founder sẽ thấy report trên next /run-monthly-review.
