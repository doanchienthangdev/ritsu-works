# Task Decompose

> Kỹ năng biến "khởi động chiến dịch Q4" thành một kế hoạch có cấu trúc trong `ops.tasks`. Bước đầu tiên của mọi orchestration đa-agent.

## Khi nào dùng

Sử dụng khi TẤT CẢ:

- Task như nhận được không thể hoàn thành bởi một role duy nhất sử dụng các tool có sẵn cho role đó
- HOẶC có 2+ sub-stream độc lập của công việc
- HOẶC task kéo dài hơn một session duy nhất (công việc nhiều ngày)
- HOẶC parent task tier là C+ và phân tách cho phép các sub-task tier thấp hơn

KHÔNG dùng khi:

- Task là một SELECT, lookup hoặc tính toán duy nhất
- Output được đưa vào ngay lập tức vào câu suy luận tiếp theo
- Tổng số lệnh gọi tool ước tính \< 4 VÀ single role

Nếu không chắc, hãy mặc định là KHÔNG phân tách. Phân tách có overhead; phân tách không cần thiết là lỗi tốn kém hơn.

## Inputs

| Input | Type | Required | Description |
|---|---|---|---|
| `parent_task_description` | string | yes | Task có độ granularity lớn như nhận được |
| `tier` | string | yes | HITL tier của parent task (A/B/C/D-Std/D-MAX) |
| `requesting_role` | string | yes | Role kích hoạt phân tách (thường là `gps`) |
| `requesting_run_id` | uuid | yes | Hàng `ops.agent_runs` hiện tại gọi điều này |
| `deadline` | timestamptz | no | Deadline do người sáng lập chỉ định nếu có |
| `decomposition_hint` | string | no | Gợi ý tùy chọn do người sáng lập cung cấp về cách chia |

## Outputs

```yaml
parent_task_id: <uuid>
child_task_ids: [<uuid>, <uuid>, <uuid>, ...]
ready_to_dispatch: [<uuid>, <uuid>]   # tasks với empty blocked_on
blocked: [<uuid>]                      # tasks chờ những cái khác
synthesis_plan: |
  Sau khi tất cả children hoàn thành, parent sẽ:
  - Tổng hợp state_payload từ children
  - Thông báo cho người sáng lập
  - Đánh dấu parent là xong
```

## Procedure

### Bước 1 — Đọc context

- Đọc `governance/HITL.md` để xác nhận xử lý tier
- Đọc `governance/ROLES.md` để biết role nào tồn tại và chúng có thể làm gì
- Đọc `knowledge/orchestration-architecture.md` (tệp anh chị em của file này) để biết quy tắc phân tách
- Tùy chọn gọi kỹ năng `episodic-recall` để xem cách các parent task tương tự trong quá khứ được phân tách

### Bước 2 — Phân loại mẫu phân tách

Phối hợp parent task với một trong 5 mẫu của Anthropic (theo `_build/notes/problem-5-multi-agent-orchestration.md`):

| Pattern | Khi nào dùng | Ví dụ |
|---|---|---|
| Routing | Loại task xác định specialist | Support ticket → phân loại → định tuyến đến agent chuyên gia |
| Parallelization | 2+ nhánh thực sự độc lập | Nghiên cứu 3 cạnh tranh cùng lúc |
| Orchestrator-workers | Subtask được khám phá khi orchestrator hoạt động | Chiến dịch đa bước với kế hoạch thích ứng |
| Prompt chaining | Các bước tuần tự với mỗi output là input tiếp theo | Outline → soạn → đánh bóng → kiểm tra thực tế |
| Evaluator-optimizer | Tạo + vòng lặp phê bình | Soạn bài → evaluator chấm điểm → optimizer sửa đổi |

Chọn MỘT mẫu chính. Các kết hợp được phép nhưng hiếm ở v1.0.

### Bước 3 — Xác định các child task

Đối với mỗi subtask, xác định:

- **`assignee_role`** — khớp với `governance/ROLES.md`. Phải là một role được định nghĩa.
- **`acceptance_criteria`** — "xong" có nghĩa là gì; cụ thể đủ để GPS có thể xác minh
- **`blocked_on`** — danh sách các ID sibling task phải hoàn thành trước (thường trống cho mẫu song song)
- **`tier`** — thường được kế thừa từ parent, nhưng có thể DROP nếu subtask không kích hoạt lý do tier của parent
- **`estimated_done_at`** — ước tính tốt nhất dựa trên các task tương tự trong quá khứ (từ episodic recall)

Anti-patterns để từ chối trong bước này:

- Sinh ra > 5 sub-task ở cùng mức → quá nhiều sub-agent song song; thiết kế lại với hệ thống phân cấp
- Sub-task không có tiêu chí chấp nhận rõ ràng → chưa sẵn sàng để ủy quyền; tinh chỉnh trước
- Sub-task được gán cho role thiếu quyền hạn cần thiết → gán lại hoặc thêm quyền qua PR (không trong kỹ năng này)
- Sub-task với tier cao hơn `hitl_max_tier` của assignee → tăng lên cho người sáng lập, không tự động tạo

### Bước 4 — Chèn parent task

```sql
INSERT INTO ops.tasks (
  status, parent_task_id, spawned_by_run,
  assignee_role, state_payload, blocked_on,
  estimated_done_at, retries_left, acceptance_criteria, tier
) VALUES (
  'in_progress',  -- parent bắt đầu in_progress, GPS đang orchestrate tích cực
  NULL,
  $requesting_run_id,
  'gps',  -- parent luôn thuộc về orchestrator
  jsonb_build_object(
    'version', 1,
    'task_kind', 'parent-orchestration',
    'pattern', $pattern_chosen,
    'description', $parent_task_description,
    'children', '[]'::jsonb,  -- điền sau bước 5
    'next_action', 'dispatch_unblocked'
  ),
  '{}',
  $deadline_or_estimate,
  3,
  $synthesis_plan,
  $tier
) RETURNING id;
```

Ghi lại `parent_task_id` được trả về.

### Bước 5 — Chèn các child task

Đối với mỗi child:

```sql
INSERT INTO ops.tasks (
  status, parent_task_id, spawned_by_run,
  assignee_role, state_payload, blocked_on,
  estimated_done_at, retries_left, acceptance_criteria, tier
) VALUES (
  CASE WHEN array_length($blocked_on, 1) > 0 THEN 'pending' ELSE 'ready' END,
  $parent_task_id,
  $requesting_run_id,
  $child_assignee_role,
  jsonb_build_object(
    'version', 1,
    'task_kind', $child_task_kind,
    'inputs', $child_inputs,
    'checkpoints', '[]'::jsonb,
    'decisions', '[]'::jsonb,
    'open_questions', '[]'::jsonb,
    'next_action', 'start'
  ),
  $blocked_on::uuid[],
  $child_estimate,
  3,
  $child_acceptance_criteria,
  $child_tier
) RETURNING id;
```

Ghi lại `id` của mỗi child. Xây dựng danh sách `child_task_ids`.

### Bước 6 — Ghi lại các chuyển đổi trạng thái ban đầu

Đối với parent:

```sql
INSERT INTO ops.task_state_transitions
  (task_id, from_status, to_status, by_run_id, reason)
VALUES
  ($parent_task_id, NULL, 'in_progress', $requesting_run_id, 'created and orchestration started');
```

Đối với mỗi child:

```sql
INSERT INTO ops.task_state_transitions
  (task_id, from_status, to_status, by_run_id, reason)
VALUES
  ($child_id, NULL, $initial_status, $requesting_run_id, 'spawned by parent ' || $parent_task_id);
```

(`$initial_status` là 'ready' hoặc 'pending' tùy thuộc vào `blocked_on`.)

### Bước 7 — Cập nhật state_payload của parent bằng child ID

```sql
UPDATE ops.tasks
SET state_payload = jsonb_set(
      state_payload,
      '{children}',
      $child_task_ids_as_jsonb
    ),
    updated_at = now()
WHERE id = $parent_task_id;
```

### Bước 8 — Trả về kế hoạch phân tách

Xây dựng và trả về YAML output. Session GPS gọi sẽ:
- Sử dụng danh sách `ready_to_dispatch` để sinh ra làn sóng đầu tiên của subagent (qua Task tool)
- Giám sát `ops.tasks` để hoàn thành child
- Khi children hoàn thành, bỏ block dependents
- Khi tất cả children xong, tổng hợp và đóng parent

## Ví dụ

### Ví dụ 1 — Mẫu Parallelization

**Input:**
```yaml
parent_task_description: "Biên soạn bản tóm tắt thông tin cạnh tranh trên top 3 EdTech AI tutoring competitors (Quizlet, Anki, Khanmigo)"
tier: C
requesting_role: gps
deadline: 2026-05-09
```

**Decomposition:**

```
parent_task: orchestration GPS của bản tóm tắt cạnh tranh
  ├── child_1: nghiên cứu Quizlet (assignee: growth-orchestrator, tier: A, blocked_on: [])
  ├── child_2: nghiên cứu Anki (assignee: growth-orchestrator, tier: A, blocked_on: [])
  ├── child_3: nghiên cứu Khanmigo (assignee: growth-orchestrator, tier: A, blocked_on: [])
  └── child_4: tổng hợp bản tóm tắt từ nghiên cứu (assignee: content-drafter, tier: C, blocked_on: [child_1, child_2, child_3])
```

**Output:**

```yaml
parent_task_id: 8a3f...
child_task_ids: [c1..., c2..., c3..., c4...]
ready_to_dispatch: [c1..., c2..., c3...]
blocked: [c4...]
synthesis_plan: |
  Khi child_4 hoàn thành (phụ thuộc vào 1-3), parent đọc state_payload c4
  cho bản tóm tắt được tổng hợp, đính kèm vào state_payload parent, đánh dấu xong.
```

### Ví dụ 2 — Mẫu Prompt chaining

**Input:**
```yaml
parent_task_description: "Soạn và xuất bản bản tin hàng tuần Ritsu cho tuần 2 tháng 5"
tier: C
```

**Decomposition:**

```
parent_task
  ├── child_1: tập hợp highlights (nghiên cứu) — assignee: growth-orchestrator, tier: A, blocked_on: []
  ├── child_2: soạn bản tin copy — assignee: content-drafter, tier: A, blocked_on: [child_1]
  ├── child_3: kiểm tra xem brand voice — assignee: code-reviewer (đóng vai là content-reviewer), tier: A, blocked_on: [child_2]
  ├── child_4: lên lịch gửi — assignee: growth-orchestrator, tier: C, blocked_on: [child_3]  # người sáng lập phê duyệt trước khi gửi
```

Lưu ý: bước SEND (child_4) kế thừa Tier C của parent; mọi thứ trước đó là Tier A vì chúng là nội bộ.

### Ví dụ 3 — TỪ CHỐI phân tách

**Input:**
```yaml
parent_task_description: "MAU hiện tại của chúng ta là bao nhiêu?"

```


## Tiêu chí chất lượng

Một lần gọi thành công:
- Tạo ra ≤ 5 children cho mỗi parent (nếu không thì thiết kế lại với hệ thống phân cấp)
- Mỗi child có một assignee_role được định nghĩa từ ROLES.md
- Mỗi child có một acceptance_criteria không trống
- Phân loại tier tuân theo các quy tắc HITL.md (parent's tier ≥ max child tier)
- Trả về trong 500ms wall-clock

## Chế độ lỗi

- **Schema chưa được cung cấp (pre-Phase B)** — trả về lỗi gợi ý "ops.tasks chưa được tạo; chạy provision-supabase-ops recipe trước"
- **Không có role phù hợp cho công việc cần thiết** — trả về lỗi với proposed new role; người sáng lập phải thêm qua PR
- **Parent task đã tồn tại cho cùng một description** — truy vấn trước; trả về existing parent_task_id với ghi chú "resuming"
- **Decomposition thất bại một phần** — gói tất cả các inserts trong BEGIN; ROLLBACK on error để không có hàng task mồ côi

## Ước tính chi phí

- ~5-10 thao tác SQL
- ~500-1500 tokens suy luận
