## When this skill runs

- Founder runs `/wiki review` (optionally `/wiki review --limit=N` or `/wiki review --type=concept`).
- Daily cron `wiki-review-queue-digest` (09:00 ICT) checks `pending_review` count; if > 0, fires Telegram heads-up: "N extractions pending /wiki review."

## Inputs

- `limit` — process up to N items per session (default 10; founder may run multiple sessions)
- `type` — optional `page_type` filter (concept / observation / decision / idea)
- `min_confidence` / `max_confidence` — optional bracket filter (default 0.6-0.85)
- `source_page_id` — optional: only review extractions from a specific source

## Outputs

- For each reviewed item: UPDATE `knowledge_extractions.founder_decision` + `founder_reviewed = true` + `founder_reviewed_at = now()`
- If item's last extraction transitions out of pending: UPDATE `knowledge_pages.review_state = 'founder_approved'` (if all accepted) OR `'founder_rejected'` (if all rejected)
- If founder chooses "merge": dispatch to `wiki-sync/merge` skill (Sprint 4)
- If founder chooses "edit": open the wiki Markdown file in $EDITOR (or surface as content for inline editing); UPDATE the file + re-INSERT corrected knowledge_extractions row
- One `ops.agent_runs` row summarizing decisions in this session

## Process

### Step 1 — Build queue

```sql
WITH pending_extractions AS (
  SELECT
    ke.id AS extraction_id,
    ke.derived_page_id,
    ke.source_page_id,
    ke.confidence,
    ke.raw_quote,
    ke.llm_model,
    dp.slug AS derived_slug,
    dp.page_type AS derived_type,
    dp.title AS derived_title,
    sp.slug AS source_slug,
    sp.title AS source_title,
    sp.source_kind,
    sp.frontmatter->>'license_status' AS license_status
  FROM ops.knowledge_extractions ke
  JOIN ops.knowledge_pages dp ON dp.id = ke.derived_page_id
  JOIN ops.knowledge_pages sp ON sp.id = ke.source_page_id
  WHERE ke.founder_reviewed = false
    AND ke.confidence BETWEEN $min_conf AND $max_conf
    AND dp.deleted_at IS NULL
    AND ($type_filter IS NULL OR dp.page_type = $type_filter)
    AND ($source_filter IS NULL OR ke.source_page_id = $source_filter)
  ORDER BY ke.created_at ASC
  LIMIT $limit
)
SELECT * FROM pending_extractions;
```

Also include dedup-queue items (page-level `review_state='pending_review'` with `frontmatter.pending_merge_candidate_id` set).

### Step 2 — Per-item review (loop)

For each item in queue:

```
┌─ Pending review N of M ─────────────────────────────────────┐
│ Derived: <derived_type> / <derived_title>                   │
│ Confidence: <conf>  Model: <llm_model>                      │
│                                                             │
│ Extracted from: <source_title>                              │
│   (license: <license_status>)                               │
│                                                             │
│ Raw quote supporting this extraction:                       │
│   > "<raw_quote>"                                           │
│                                                             │
│ Current derived page summary:                               │
│   <first 200 chars of wiki/<type>/<slug>.md body>           │
└─────────────────────────────────────────────────────────────┘
```

AskUserQuestion options:
1. **Accept** — extraction is correct as-is. UPDATE founder_decision='accepted'.
2. **Reject** — extraction is wrong. UPDATE founder_decision='rejected'. If this was the LAST extraction tying derived_page to source, founder decides whether to soft-delete the derived_page (separate prompt).
3. **Edit** — extraction is mostly right but title/summary needs adjustment. Open derived page Markdown for inline edit. UPDATE founder_decision='edited'.
4. **Merge** — this entity is the same as an existing entity. Dispatch to `wiki-sync/merge`; founder picks the canonical slug.

For dedup-queue items (page-level pending merge):
1. **Confirm merge** — yes, these are the same. Dispatch to `wiki-sync/merge` with canonical = existing entity.
2. **Reject merge** — no, these are distinct. UPDATE both pages: `review_state='founder_approved'`, clear `pending_merge_candidate_id` from frontmatter.
3. **Skip for now** — leave in queue; next session.

### Step 3 — Page review_state rollup

After each extraction reviewed, recompute page-level review_state:
```sql
WITH ext_summary AS (
  SELECT
    derived_page_id,
    COUNT(*) AS total,
    SUM(CASE WHEN founder_reviewed = false THEN 1 ELSE 0 END) AS still_pending,
    SUM(CASE WHEN founder_decision = 'accepted' THEN 1 ELSE 0 END) AS accepted,
    SUM(CASE WHEN founder_decision = 'rejected' THEN 1 ELSE 0 END) AS rejected
  FROM ops.knowledge_extractions
  WHERE derived_page_id = $page_id
  GROUP BY derived_page_id
)
UPDATE ops.knowledge_pages SET review_state = CASE
  WHEN ext_summary.still_pending > 0 THEN 'pending_review'
  WHEN ext_summary.rejected = ext_summary.total THEN 'founder_rejected'
  ELSE 'founder_approved'
END
WHERE id = $page_id;
```

## HITL discipline

- **Tier B per item.** Each AskUserQuestion is its own gate. Founder may abort mid-session; partial progress saved to DB.
- **Telegram daily digest** (cron `wiki-review-queue-digest`) is Tier A (read-only Postgres + Telegram bot call).

## Cost

- Per item: ~$0 (no LLM in review — just DB reads + AskUserQuestion + DB writes)
- Task_kind: `wiki-review-batch` ($0.20 cap per spec §0; rarely reached unless LLM helps suggest synonyms during merge dispatch)

## Failure modes

| Symptom | Response |
|---|---|
| Founder picks "Edit" but $EDITOR not set | Fallback: surface page content as AskUserQuestion prompt for inline edit (multiline); save back to file via Write tool. |
| Founder picks "Merge" but target slug doesn't exist | Dispatch to merge skill which prompts for canonical slug (search-as-you-type from existing knowledge_pages). |
| Cron digest fires but founder doesn't respond for N days | After 7 days of unresponded pending, increase Telegram heads-up frequency to per-3-day. After 14 days, escalate via daily reminders. Pending count never auto-clears. |
