> The template that every brain-aware skill follows for `## Brain context` sections.

This skill is the canonical source for HOW skills should interact with gbrain. Skills do not invoke this skill at runtime; they author a `## Brain context` section in their own SKILL.md by following the template below. Capability `gbrain-operational-brain` v1.0 (Phase 7 Sprint 2) extends 13 brain-relevant skills with this exact section pattern.

## When a skill needs a `## Brain context` section

Per the brain-relevance audit (`refs/03-component-audit.md` Zone 3), a skill needs this section if it meets one of:

- **Operational entity adjacency** — skill reads/writes about people, companies, meetings, ideas, concepts, decisions (the 6 gbrain page types)
- **Cross-session memory** — skill benefits from prior-task context that lives in brain pages
- **Pipeline coupling** — skill is part of a flow (e.g., CLA Phase 1-8) where each phase auto-creates a brain narrative page

Skills that are domain-irrelevant (pure cost analytics, compliance checks, external→internal pipelines) DO NOT need this section. Maintain the explicit SKIP list:

`cost-optimization-review`, `cost-report`, `ai-disclosure-check`, `docs-engine`, `eval-evo`, `wiki-sync`, `resolver-query`, `core-management`

## The canonical `## Brain context` section template

Insert AFTER the skill's `## When to use` section, BEFORE `## Inputs`:

```markdown
## Brain context

> Per capability `gbrain-operational-brain` v1.0 (Phase 7 Sprint 2). Skill is brain-aware: reads relevant brain pages at start; writes a narrative page at end (when applicable). Per `06-ai-ops/skills/brain-write-discipline/SKILL.md` template.

### READ (before reasoning)

Invoke at start of skill execution:

```
mcp__gbrain__search "\<topic keywords from task>" → top 5 results
```

Read top 1-3 results that are obviously relevant. Cost: ~$0.005/skill-invocation (cost_bucket `gbrain.shared.search`).

**Skip the read when:**
- Skill's caller role has `brain_affinity: none` (per `governance/ROLES.md`)
- Task has no operational entity context (e.g., pure compute)
- Founder-set session flag `--no-brain` is active

### WRITE (after producing artifact, if applicable)

If this skill produces an output worth remembering as operational truth:

```
mcp__gbrain__put_page \{
  page_type: \<ideas|concepts|meetings|companies|people>
  slug: \<auto-derived from skill output context>
  title: \<descriptive title>
  body: \<narrative summary, max ~1500 tokens>
  frontmatter: \{
    source_skill: \<this skill name>
    source_run_id: \<ops.agent_runs.id>
    capability_id: \<ops.capability_runs.id if CLA-coupled>
  }
}
```

HITL Tier B (notify-first-then-batch):
- Write happens immediately (no blocking)
- Emit `ritsu.gbrain.write_committed` event
- `hitl-router` batches notify into daily Telegram summary
- Founder presses [Undo] within 1h to revert (calls `mcp__gbrain__archive_page`)

Cost: ~$0.02/page write (cost_bucket `gbrain.<role>.put_page`).

**Skip the write when:**
- Skill output is purely diagnostic (no operational value)
- Caller role lacks `mcp_servers: [gbrain]` grant per `governance/ROLES.md`
- Founder-set session flag `--no-brain` is active
- gbrain MCP wrapper returns "degraded" (cost cap reached; see `knowledge/economic-architecture.md` v1.1 addendum)
```

## Why this pattern (not centralized router)

The Q3 v2 brainstorm decision rejected a centralized brain-first-lookup router skill in favor of **decentralized model-led** access. Reasoning:

- Claude Code's native pattern: model decides when to use available tools based on `## Brain context` documentation in the skill
- Centralized router adds latency + token cost + failure mode (router down = nothing works)
- Decentralized respects per-skill judgment about brain relevance

The trade-off: 13 SKILL.md files must each maintain a consistent `## Brain context` section. The `brain-write-discipline` skill is the contract that keeps them consistent.
