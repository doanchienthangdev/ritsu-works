## 41.1 Bài toán — third leg of the write-loop trinity

### 41.2.1 Separate-commands vs merge-into-/evolve

**Options considered** (Phase 4):

**Option A — v3.0 separate-commands + shared-infrastructure** (CHOSEN)
- Hai commands phân biệt: `/update <type> <name> --refs=<csv>` và `/evolve <type> <name>` (no refs)
- Shared infrastructure: universal entity-edit lock, eval-evo skill suite, audit tables
- Pros: founder mental model rõ (update = ingest external, evolve = improve internal); convention fit (1 verb / 1 intent); future divergence supported (webhook /update v2.0, mass /update v1.2)
- Cons: ~$3-5 extra build vs merge; 2x command surface (mitigated bằng thin orchestrator facades)

**Option B — v2.0 merge into /evolve với --refs flag**
- `/evolve <type> <name> [--refs=<csv>]` — refs là optional flag
- Pros: $4-7 build, single command surface, simpler routing
- Cons: hidden flag behavior (founder phải nhớ --refs là different code path); "evolve" verb connote self-improvement (gây nhầm); /evolve hook awkwardness; future flag-overload anti-pattern

**Option C — v1.0 standalone (duplicate infrastructure)**
- /update có own orchestrator + own lock + own audit
- Pros: zero shared dependency = zero cross-flow regression
- Cons: duplicates ~80% eval-evo logic; 2x maintenance burden; encourages divergence over time

**Decision rationale (auto-resolved Phase 4):** Founder pre-committed Option A trong `/plan-ceo-review` morning session + `/plan-eng-review` afternoon session. CxO (@cto) concurred. Phase 4 honored "do not re-litigate" instruction trong /cla propose prompt body.

### 41.2.2 K4 ratchet mode

**Karpathy K4** (chương 37 §37.4) = score post-iter must ≥ score pre-iter (else auto-revert). /evolve uses strict K4.

**/update problem:** refs-driven changes có inherent variance. Founder paste 3 đoạn Kotler vào skill — diff lớn 50 dòng — score variance ±3-5 pts là noise, không phải regression.

**Decision:** Mode-aware K4 — `/update` allows `score_post >= score_pre - 5` (5pt slack). `/evolve` keeps strict (no slack). Slack documented + audit-logged để monitor false-positive revert rate.

### 41.2.3 Citation spine

Per founder Q1 (Phase 1): mỗi proposed_change phải trace về **raw_quote** từ ref chunk cụ thể. Không cho phép LLM fabricate.

**Implementation:** NEW table `ops.evolve_extractions` (Sprint 2 migration 00040):

```
ops.evolve_extractions:
  id uuid PRIMARY KEY
  agent_run_id uuid REFERENCES ops.agent_runs(id) CASCADE
  ref_path text NOT NULL           -- citation source
  ref_chunk_index integer NOT NULL
  raw_quote text NOT NULL (≤ 2000) -- verbatim text from ref
  proposed_change text NOT NULL    -- structured change
  confidence numeric(3,2) (0..1)
  review_state CHECK IN (auto_accepted | pending_review |
                         rejected_low_confidence |
                         founder_accepted | founder_rejected | founder_edited)
```

**3-bucket confidence rounding:**
- `>= 0.85` → `auto_accepted` (terminal-on-insert; goes to propose phase)
- `0.6-0.85` → `pending_review` (founder reviews via `/update review`)
- `< 0.6` → `rejected_low_confidence` (terminal-on-insert; logged but skipped)

**State machine trigger** (migration 00040): `ops.evolve_extractions_check_review_transition` enforces legal transitions:
- pending_review → founder_\{accepted|rejected|edited} (founder review)
- auto_accepted, rejected_low_confidence: terminal-on-insert (UPDATE blocked)
- founder_* states: terminal once set

DB trigger = single source of truth cho review state machine. Validator invariant `evolve-extractions-review-state-machine-valid` flipped `deferred → live` khi migration 00040 landed.

### 41.2.4 Universal entity-edit lock

## 41.5 Design lessons trích từ session này

### Lesson 1 — Brainstorm-then-execute pattern reduces /cla overhead

v1.1 + v1.1.1 ship qua `/cla extend update` (sub-flow) thay vì /cla propose (full ceremony). Pre-existing brainstorm artifacts trong `.archives/cla/update/v1.1-brainstorming/` đóng vai trò "design spec" — `/cla extend` workflow phase 1-5 collapsed thành "read brainstorm + go".

**Generalizable rule:** Khi founder có muse-session-output hoặc explicit design doc → `/cla extend` thay vì re-running architect ceremony.

### Lesson 2 — Single-session full-stack ship is feasible với compressed phases

v1.0 từ Phase 0 → Phase 8 trong 1 session founder time ~2 giờ. Sprint plan estimated 12 calendar days. Compression factor: ~80x.

**Why feasible:**
- Auto-approval at Tier C gates (founder bias toward "approve + execute" via AskUserQuestion option 1)
- Composition-heavy architecture (Sprint 3 orchestrator chỉ ~330 LOC vì delegates to shared eval-evo skills)
- Test-first approach (each Sprint commits 30-60 tests immediately)
- pnpm check + CI hash-drift validator catches mistakes within seconds

**Why NOT generalizable to all caps:** /update reused 80%+ infrastructure từ /evolve (Chương 37). Greenfield caps (gbrain Chương 18, resolver Chương 38) needed longer cycles vì building primitives mới.

### Lesson 3 — Auto-classifier blocks save the founder

Sprint 1 PR #118 commit `992236c` initially landed on **`main` branch** không phải feature branch — vì Bash command chuỗi `cd /Users/doanchienthang/ritsu-works && git ...` đã `cd` vào root repo (where main checked out) thay vì worktree. Recovery via fast-forward worktree's branch + reset main back. Auto-classifier blocked `git reset --hard` requiring founder authorization — correctly per Tier C in HITL.md.

**Memory saved:** `feedback_worktree_git_commands_stay_in_worktree.md` ghi nhận quirk. Future Claude sessions trong worktree không lặp lại lỗi.

### Lesson 4 — Honest gap reporting unlocks v1.1.1

Founder asked: *"giả sử tôi muốn update 1 file trong 00-core thì phải dùng lệnh gì?"* (referring to v1.1's REFUSE on Tier 1 paths). Claude's first response: honest enumeration của 2 lựa chọn xấu (hand-edit + PR; /cla extend) + proposed v1.1.1 fix với D-Std ceremony as Option 1.

Founder picked option 1. /update tier1-file ship trong cùng session ~30 phút.

**Pattern:** Surface gaps + propose minimum-viable fix + AskUserQuestion → founder decides → execute. Don't pretend gap doesn't exist.

### Lesson 5 — CI infra failures distinct from code failures

PR #118 CI initially returned `403 Your account is suspended` trên GitHub Actions runner. Memory saved (`reference_github_actions_transient_suspended.md`): transient infra issue, not real suspension. Verified via web access + `gh auth status` + re-run. Both passes on second try.

**Diagnostic checklist** (Memory): web access OK + `gh auth status` active + `gh api repos/<owner>/<repo>` returns + `gh api repos/.../actions/permissions` shows enabled + re-run passes → transient.

### Lesson 6 — Path-tier classifier is the safety primitive cho generic file mode

v1.1 Sprint 2 file mode — NO playbook (no scoring rubric for arbitrary files) → K4 ratchet inapplicable. Replacement safety:

1. **Path-tier classifier** (`knowledge/update-file-paths.yaml`, 38 globs) — Tier 1 paths REFUSED with forward; others Tier B/C
2. **Phase 0a** runs BEFORE distill — deterministic, no LLM cost on refused paths
3. **Phase 6.5 founder approval** — mandatory AskUserQuestion at install time (Apply/Edit/Reject/Promote-to-PR) — replaces K4
4. **File-size + binary safety** — > 200 KB refused; non-UTF-8 refused
5. **Generic distill prompt RULE 5 SECURITY** — refuses extractions injecting code/secrets/HITL changes

**Generalizable:** Whenever a system bypasses a quality ratchet (because rubric doesn't apply), substitute multiple human-in-loop checkpoints upfront. Founder agency at every decision point.

### Lesson 7 — Symmetric ceremony pattern (D-Std for safety-critical types)

`/update hook` (v1.1 Sprint 1) shipped D-Std magic-phrase ceremony per invocation. v1.1.1 reused same pattern for `/update tier1-file`. Both call same Phase -1 orchestrator code path with `entity_type IN ('hook', 'tier1-file')` check.

**Generalizable:** Když implementing safety-critical entity type, look for existing ceremony pattern + extend (don't reinvent). Single Phase -1 cover multiple types via input enum.

## 41.8 Reflection — `/update` là gì? Cái gì /update KHÔNG là?

`/update` **không phải**:
- General-purpose file editor (use hand-edit cho ≤ 5 LOC)
- AI-pair-programming (use /evolve cho self-improvement không refs)
- Capability creation (use /cla propose)
- Mass refactoring (deferred to v1.2)
- Webhook-driven auto-runner (deferred to v2.0)
- D-MAX path mutator (refuses governance/SECRETS.md, .mcp.json, supabase/migrations/)

`/update` **là**:
- Refresh-from-refs verb cho 4 v1.0 + 5 v1.1 + 1 v1.1.1 = 10 entity types
- Citation-disciplined (ops.evolve_extractions trace mỗi change về raw_quote)
- Tier-classified (trivial/medium in-place B; structural ABORT; tier1 always C)
- Cost-bounded ($30/mo cap, $1.50/run hard cap)
- Audit-trailed (ops.agent_runs, ops.entity_edit_locks, ops.audit_log Tier C overrides)
- Composable (orchestrator never calls Anthropic API; delegates to 5 shared eval-evo skills)

**Trinity completed:**
- `/cla create` → tạo capability mới (ý tưởng → architecture → ship)
- `/evolve self-improve` → eval+propose+score loop (memory-driven; no refs)
- `/update ingest external truth` → distill từ refs + apply (citation discipline; mode-aware K4)

Ba verbs này collectively là **write-loop layer** của ritsu-works AI-native operations. Không có /update thì refresh là manual; không có /cla thì capability creation là ad-hoc; không có /evolve thì self-improvement không repeatable. Một verb thiếu = ecosystem-level gap.
