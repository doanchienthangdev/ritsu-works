> Phần III nói về **what to build**. Phần IV bắt đầu **how to actually build**. Bắt đầu bằng cách layout files.

## 11.1 Tại sao layout matters

Một file in wrong place = drift theo thời gian. "Brand voice trong Notion" lại trở thành "brand voice rải rác giữa 4 nơi" sau 3 tháng. Layout fixes the gravity:

- **Tier 1 files trong git** → version-controlled, reviewable, recoverable
- **Tier 2 schemas trong manifest** → discoverable, cross-referenceable
- **Workspace plane separate** → low-ceremony for drafts, không pollute Tier 1

Cấu trúc dưới đây là Ritsu's actual repo structure sau Phase A. Có thể fork làm template.

## 11.3 Top-level files

### `README.md`

Brief intro to the repo. Audiences:

- **Founder** — pointer to current ROADMAP, CLAUDE.md
- **Future contributors** — overview of structure
- **Outside reader** — context if they stumble on the repo

Convention: keep \< 100 lines. Detailed docs live elsewhere.

### `CLAUDE.md`

Entry point cho Claude Code sessions. Per Bài #3, **lean** (\< 2K tokens). Use `@imports` for full content of governance/charter/architecture.

### `.gitignore`

Critical patterns:

## 11.11 What's NOT in this repo

Explicit non-locations:

- **Customer data.** Lives in separate Supabase project (`ritsu` = Product DB).
- **Source code of the product itself.** Separate repo.
- **Secret values.** In secret manager (1Password Service Accounts).
- **Internal Slack/Telegram conversations.** Stay in those tools.
- **Customer support tickets raw.** In Helpscout/Intercom.

This repo is **the operating system of the company**, not the company itself. Product, customer data, conversations live in their respective tools.

## 11.12 Naming conventions

- **Files in Tier 1:** `kebab-case.md`
- **SQL tables:** `snake_case` in `ops` schema
- **Role slugs:** `kebab-case` (e.g., `growth-orchestrator`)
- **Skills:** `kebab-case-action` (e.g., `cost-report`, `task-decompose`)
- **Secrets:** `UPPER_SNAKE_CASE_WITH_SCOPE` (e.g., `ANTHROPIC_GPS_KEY`)
- **Hooks:** `kebab-case.md` matching `pre-tool-*`, `post-tool-*` pattern
- **Brainstorm notes:** `problem-N-short-name.md`

Conventions enforced by:
- Hooks (e.g., `pre-tool-secrets` validates SECRET_NAME format)
- Code reviewer (`code-reviewer` role checks PR for naming compliance)
- Manual review (founder approves new conventions via PR)
