## 16.4 Workaround tạm vs proper extension

### Workaround (NOT recommended)

Each workflow as 1 giant skill (`daily-lead-gen-skill/SKILL.md` 800 lines). Fails:
- Skill testing impossible
- No reuse (steps duplicated)
- No per-step versioning
- No step-level audit
- Hard for AI agent to reason about

### Proper extension — Bài #9: SOP Architecture

4 axes (Phase A pattern):

#### Axis 1 — SOP definition format

Tier 1 declarative YAML files. Schema:

```yaml
# 01-growth/sops/SOP-GROWTH-001-daily-lead-generation.yaml

id: SOP-GROWTH-001
version: 1.2.0
title: Daily Lead Generation Batch
status: active
home_pillar: 01-growth
owner_role: growth-orchestrator
hitl_tier: B  # whole-SOP tier

triggers:
  - type: scheduled
    schedule_id: daily-lead-gen  # references Bài #8 schedules.yaml
  - type: manual
    invocation: "/sop run SOP-GROWTH-001"

inputs:
  - name: campaign_theme
    default: "general-edtech"

estimated_cost_usd: 0.85
estimated_duration_min: 12

steps:
  - id: step-1-define-icp
    title: Define ICP filter
    invoking_role: growth-orchestrator
    skill: define-icp-query
    inputs:
      icp_spec: "@knowledge/icp.yaml"
      campaign_theme: "{{ inputs.campaign_theme }}"
    outputs:
      apollo_query: object
    on_failure: abort
    timeout_sec: 60

  - id: step-2-apollo-search
    depends_on: [step-1-define-icp]
    skill: apollo-search
    inputs:
      query: "{{ steps.step-1-define-icp.outputs.apollo_query }}"
      max_results: 500
    on_failure:
      action: retry
      max_retries: 2
      backoff: exponential

  - id: step-3-email-verify
    depends_on: [step-2-apollo-search]
    skill: findymail-verify
    quality_gate:
      condition: "pass_rate >= 0.50"
      on_fail: escalate

  # ... steps 4-7

dependencies:
  skills: [...]
  mcp_servers: [apollo, findymail, hubspot, instantly]
  knowledge_files: [knowledge/icp.yaml]
  secrets: [APOLLO_GROWTH_KEY, FINDYMAIL_GROWTH_KEY, ...]

quality_metrics:
  target_leads_per_run: 30  # net-new after dedup
  alert_if_leads_below: 10
```

Per-step granularity. Built-in error handling (`on_failure`). Quality gates (`quality_gate`). Dependency tracking.

```
├── 05-ai-ops/                    ← existing
├── 06-finance/sops/SOP-FINANCE-001-...
└── 07-compliance/sops/SOP-COMPLIANCE-001-...
```

Pillar template (`_build/templates/pillar/`):

```
<pillar-name>/
├── README.md           # pillar description, KPIs, owner role
├── orchestrator.md     # pillar-level coordination logic
├── sops/               # SOPs ở pillar
├── skills/             # pillar-specific skills
└── knowledge/          # pillar-specific knowledge
```

Tại sao per-pillar:
- Cohesion (SOPs cluster theo business domain)
- Ownership (pillar owner role responsible)
- Discovery (`01-growth/sops/`)
- Manifest reconciliation (`pillars` section in manifest.yaml)

#### Axis 3 — SOP execution engine

**`sop-execute` skill** + reuse `ops.tasks` + new `ops.sop_runs` index table.

Flow:
```
1. Load SOP YAML
2. Validate dependencies (skills, MCP, secrets, knowledge)
3. Insert ops.tasks row, task_kind='sop-execution', state_payload includes sop_id, current_step
4. For each step in order:
   a. Resolve inputs (templating from prior outputs)
   b. Pre-flight checks (HITL step-level if specified, budget, dependencies)
   c. Invoke skill via subagent (Bài #5 pattern)
   d. Capture outputs to state_payload.steps[step.id].outputs
   e. Quality gates check
   f. on_failure handler
   g. Update ops.task_state_transitions
5. Final summary writes to ops.sop_runs
6. Trigger side effects (Telegram digest, etc.)
```

`ops.sop_runs` table:

```sql
CREATE TABLE ops.sop_runs (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  sop_id          text NOT NULL,
  sop_version     text NOT NULL,
  task_id         uuid REFERENCES ops.tasks(id),
  triggered_by    text NOT NULL,  -- 'scheduled' | 'manual' | 'event'
  trigger_ref     text,
  status          text NOT NULL,  -- pending | running | done | failed | aborted | escalated
  current_step    text,
  steps_completed text[],
  steps_failed    text[],
  inputs          jsonb,
  outputs         jsonb,
  total_cost_usd  numeric(10,6),
  started_at      timestamptz NOT NULL DEFAULT now(),
  completed_at    timestamptz,
  error_summary   text
);
```

Step-level state in `ops.tasks.state_payload`:

```json
{
  "task_kind": "sop-execution",
  "sop_id": "SOP-GROWTH-001",
  "current_step": "step-3-email-verify",
  "steps": {
    "step-1-define-icp": { "status": "done", "outputs": {...} },
    "step-2-apollo-search": { "status": "done", "outputs": {"raw_leads_count": 423} },
    "step-3-email-verify": { "status": "running" },
    "step-4-dedup": { "status": "pending" }
  }
}
```

Tại sao reuse ops.tasks (không tạo new state machine):
- ops.tasks already has parent_task_id, state_payload, blocked_on
- SOP execution = 1 parent task + N step-tasks
- Reuse audit + cost attribution
- ops.sop_runs là **summary index** for SOP-level analytics

#### Axis 4 — Authoring discipline + governance

**3 rules:**

1. **When to codify:** Workflow runs **3+ times** ad-hoc → codify as SOP. Hook tracks task patterns; flags candidates.
2. **SOP must be testable:** Each step có clear inputs, outputs, success criteria. Quality gates explicit.
3. **SOP-level tier ≥ max(step tiers):** Whole-SOP HITL tier ≥ highest tier of any step. Prevents Tier-B-SOP containing Tier-C step (escalation gap).

**Hook `pre-sop-execute`:**
```
on sop-execute skill invocation:
  1. Validate SOP YAML schema
  2. Check dependencies exist (skills, MCP, secrets)
  3. Cross-check SOP tier ≥ max step tiers
  4. Budget pre-flight (sum estimated step costs vs role budget)
  5. HITL pre-flight (if SOP tier C+, queue founder approval)
  6. Concurrency check (active SOP run of same SOP_id?)
on success: allow execution
on violation: escalate or block
```

**Skills:**
- `sop-author` — helps founder/agent author SOPs (decompose + identify skills + draft YAML + validate + PR)
- `sop-candidate-detector` — scans ops.agent_runs weekly, flags workflows running 3+ times ad-hoc

## 16.7 Lessons captured

1. **SOP ≠ skill ≠ task decomposition.** Three distinct abstractions.
2. **YAML > Python for SOP definition.** Declarative, version-controlled, agent-readable.
3. **Per-pillar storage > global sops/ folder.** Cohesion + ownership + discovery.
4. **Reuse ops.tasks, don't create new state machine.** state_payload covers step orchestration.
5. **Hook + skill defense pattern continues.**
6. **Authoring discipline is content-level, not infrastructure.**
7. **Pillars emerge from SOP need.** Phase A had only `05-ai-ops/`; SOPs need pillars (growth, customer, etc.).
8. **SOP tier ≥ max step tier.** Escalation gap prevention.

## 16.9 Anti-patterns

- ❌ SOP as 1 giant skill (defeats per-step audit, versioning, error handling)
- ❌ SOP in code (Python file) — breaks "content as runtime"
- ❌ Global sops/ folder — loss of pillar cohesion
- ❌ Step state in skill memory — must be ops.tasks.state_payload
- ❌ SOP without quality gates — silent failures
- ❌ Auto-promote ad-hoc workflow to SOP — founder must approve codification
