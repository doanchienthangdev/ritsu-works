### Forensic — timing reconstruction

Compare req/resp file timestamps:
```
req-2f93... attempt=0 enqueued at 16:20:25
req-attempt=1 enqueued at 16:22:27       ← 122s sau
req-attempt=2 enqueued at 16:24:29       ← 122s sau nữa
```

### Root cause

Vendor `vendor/skillopt/skillopt/envs/ritsu_skill/adapter.py` hard-coded:
- `exec_timeout=120` (rollout)
- `judge_timeout=120` (judge)
- `timeout=180` (optimizer reflect)
- `retries=3` ở 3 call sites

Trong-session orchestrator latency:
- Mỗi `Task()` dispatch tới subagent: 5-15 giây
- Batch overhead (request scan + classify + write-response + batch-complete): 5-10 giây
- Total per response cycle: 15-30 giây
- Nếu 4 dispatches parallel trong 1 message: 30-60 giây cho cả batch

120s/attempt × 3 attempts = 360s tổng budget. Hoàn toàn không đủ cho human-paced in-session orchestrator.

**Vendor được thiết kế cho direct OpenAI/Anthropic API calls** (sub-second latency). Bridge insert một LLM dispatch (5-15s) giữa request-write và response-write — trainer's tight retry policy không tolerate được.

### Fix

3 layers:
1. `scripts/skillopt/upstream-patches/configs-ritsu_skill-default.yaml`: `judge_timeout` + `exec_timeout` 120 → **1800** (30 phút/attempt)
2. `scripts/skillopt/upstream-patches/ritsu_skill/adapter.py`: 3 sites `retries=3` → **retries=10**; optimizer site `timeout=180` → **1800**
3. `06-ai-ops/skills/eval-evo/skillopt-runner/SKILL.md`: cfg template + env `SKILLOPT_FILE_QUEUE_TIMEOUT_S=1800` belt-and-suspenders

Belt-and-suspenders: 1800s × 10 retries = 5 GIỜ budget per call. Generous cho mọi human pacing.

## 42.3 Lớp 3 — Patch schema mismatch silent drop

### Triệu chứng

Sau khi fix Lớp 4, run 2 vẫn skip × 3. Log mới:
```
[1/6 done] hard=0.7500 soft=0.7500
[2/6 done] failure_patches=0 success_patches=0
[skip] no usable patches — skill unchanged
```

`hard=0.75` (varied!) — chứng tỏ rollouts + judges đã accept responses. Vấn đề giờ ở patch parsing. `failure_patches=0` nghĩa là tôi propose patch nhưng trainer extract 0 edits.

### Root cause forensic — 3 layers nested

Đi từ orchestrator (top) xuống vendor apply_patch (bottom):

**1. Agent file `.claude/agents/skillopt-optimizer-reflect.md` documented schema SAI:**
```json
{
  "edits": [
    {
      "op": "add" | "delete" | "replace",       ← "add" không tồn tại!
      "target": "L42-L48",                       ← line ranges KHÔNG SUPPORTED!
      "new_text": "..."                          ← vendor đọc "content"!
    }
  ]
}
```

**2. Env adapter `vendor/skillopt/skillopt/envs/ritsu_skill/adapter.py:415-429`** expect FLAT top-level:
```python
parsed = _parse_strict_json(response)
if not parsed or not isinstance(parsed.get("edits"), list):
    print("unparseable response")    # ← My response thất bại check này nếu nested
    return None
return {"patch": {"edits": parsed["edits"]}, "source_type": kind}   # ← Wrap internally
```

So adapter expects `{"edits": [...]}` FLAT, sau đó nó WRAP thành `{"patch": {"edits": ...}}` cho vendor reflect.py. Subagent KHÔNG được wrap mình.

**3. Vendor `apply_patch` reads:**
```python
# vendor/skillopt/skillopt/optimizer/skill.py
def _edit_fields(edit):
    op = edit.get("op", "")              # ← "add" sẽ vào status="skipped_unknown_op"
    content = edit.get("content", "")    # ← KHÔNG đọc "new_text"
    target = edit.get("target", "")      # ← target IN skill (substring match)
    return op, content, target

# Only 4 ops supported: append / insert_after / replace / delete
# Anything else → skipped_unknown_op
```

### Triple-blind silent drop

Mỗi layer "thất bại đẹp đẽ" — không exception, không error log, chỉ return None / 0 items:
1. Subagent emit `{"op":"add", "new_text":"..."}` 
2. Adapter `parsed.get("edits")` returns list → check pass → wrap to `{"patch":{"edits":[...]}}`
3. Vendor reflect.py `truncate_payload(result["patch"], edit_budget, "patch")` — works on dict, gets `result["patch"]["edits"]` list
4. Apply step `_edit_fields()` reads `op="add"` → status `skipped_unknown_op`, reads `content=""` (because field name is `new_text`) → empty content
5. Trainer counts edits with valid `op`+`content` → **0**
6. Log: `failure_patches=0`

Mỗi layer làm "đúng" theo defensive contract — không crash, không exception. Nhưng combined: silent drop của 100% patches. **Đây chính là "Triple-blind silent drop" anti-pattern** — defense-in-depth đến mức loss-of-visibility.

### Fix

Rewrite agent file schema documentation với:
1. Schema example FLAT `{"edits": [{...}]}` (không có top-level `patch` wrapper)
2. 4-op enum chính xác: `append | insert_after | replace | delete`
3. Field name `content` (không phải `new_text`)
4. Schema gotchas section cite exact vendor file:line + describe nesting + ops + field names
5. "Edit ops semantics" subsection list semantic của từng op (append at end, insert_after target, replace target, delete target)

Plus playbook updates (`06-ai-ops/skills/eval-evo/playbooks/`):
- `skill-skillopt.md`: add `allowed_paths_for_proposer_notes` block về schema discipline
- `agent.md`: expand C5 sub-criterion để rate "downstream parser citation discipline"

### Validation

Run 3 (post-L3-partial-fix): `accept=0 reject=2 skip=1`. **First time patches FLOW THROUGH pipeline**. Step 1 still skipped (tested nested schema before final fix); steps 2+3 reject (correct trainer behavior — doc-only patches don't move runtime score, trainer's K4 gate rejects).

Run 4 (full fix + automated driver): `accept=0 reject=3 skip=0`. **Clean** — 100% rejects, 0 silent drops.

## 42.7 Bài học cho future capability authors

### Anti-pattern: triple-blind silent drop

Khi viết một subagent có output được parse downstream qua nhiều layer:
1. Agent định nghĩa output schema
2. Adapter parse + transform schema
3. Vendor consumer apply schema

Mỗi layer có defensive try/catch + "return None on parse fail". Hợp nhau = silent loss. Nếu agent docs lệch với vendor expectation, không layer nào CRASH — chỉ silently degrade thành no-op. **Solution**: agent docs MUST cite EXACT downstream parser file:line + describe schema, không reply only on common-sense.

Playbook `agent.md` C5 rubric expanded (post-PR #138) để rate "downstream parser citation discipline" như một explicit grading dimension.

### Anti-pattern: in-session orchestrator latency

Vendor tools (SkillOpt, frameworks tương tự) được tuned cho direct API calls với sub-second latency. Khi bridge insert một LLM dispatch (5-15s) giữa request và response, vendor's retry/timeout assumptions break. **Solution**: bump timeouts ≥30 phút/attempt + retries ≥10. Belt-and-suspenders qua env vars cho callers không pass explicit timeout. Documentation Layer 4 fix in capability runbook + memory.

### Anti-pattern: data-prep vs mechanism conflation

Đầu session, founder hỏi "tại sao sandbox không đổi?" — câu trả lời lười là "data prep không tốt". Câu trả lời ĐÚNG là "có 4 lớp issues stacked":
- L1: --dry-run (mode)
- L2: data prep (rubric)
- L3: patch schema (code)
- L4: retry timeout (config)

Fix L1+L2 alone, vẫn skip × 3 because L3+L4 chưa fix. Bóc layers theo thứ tự + validate từng cái với 1 dry-run = forensic methodology cho self-improvement capability.

### Tier B decision: bypass /cla fix ceremony (chấp nhận tradeoff)

Founder + tôi bypass `/cla fix evolve` cho cả L4 + L3 fix. Cost:
- Lost: `ops.capability_runs` row với phase events; sprint plan documentation; full audit lineage in capability lifecycle
- Gained: ~30 min - 2 hours per fix saved (no /cla ceremony rerunning diagnostic I already had in session)

Compromise: created `ops.agent_runs` + `ops.run_summaries` + `ops.events` trail (4 runs documented); updated memory file. **Retrospective `/cla fix` entry post-PR-138 = nice-to-have, not blocker**. For larger fixes (architecture-level changes, new sub-flow design), DO use /cla fix.

## 42.9 Câu hỏi cho founders apply pattern này

1. **Khi nào bạn dùng /evolve vs /update vs /cla fix?** /evolve = improve quality của entity hiện hữu qua signal data. /update = ingest external truth (book/wiki/spec) vào entity. /cla fix = explicit bug fix với /cla ceremony lineage.

2. **Tại sao L1 → L4 thứ tự ngược lại với fix order?** L1 (mode) là user choice — chọn dry-run hay không. L2 (data) deferred vì cost. L3 (code) + L4 (config) là mandatory mechanism fixes. Fix order: L4 → L3 → (L2 deferred) → L1 (founder decision).

3. **Sandbox vs production discipline trong /evolve.** Default sandbox flow: `runtime/sandboxes/<flat>/SKILL.md` is working copy. Phase E ghi sandbox, founder manual `cp sandbox → production` sau khi review. `--apply` flag switch sang production-edit với git stash safety net. Đầy đủ rebuilds — production NEVER edited automatically.

4. **Khi nào cần update playbook?** Sau MỖI capability bug fix có lesson tổng quát. PR #138 — schema discipline lesson áp dụng cho TẤT CẢ subagent có output downstream-parsed (>= 5 agents trong repo hiện tại). Playbook Chương 42 captures it; rubric `agent.md` C5 enforces it going forward.
