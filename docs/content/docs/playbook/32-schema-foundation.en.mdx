## 32.3 Migration architecture

### Numbering convention

```
00001-09999: generic core (boilerplate)
10001-19999: project-specific domain tables
20001-29999: project-specific RLS extensions
30001-39999: project-specific seed data
```

### Why 5-digit prefix?

Allows interleaving when boilerplate updates ship after project starts:

```
00001_initial_extensions.sql       (boilerplate v1.0)
00002_ops_core_tables.sql          (boilerplate v1.0)
...
00010_rls_policies.sql             (boilerplate v1.0)
00011_audit_log_partitioning.sql   (boilerplate v1.1, added later)
10001_ritsu_lessons.sql            (project Wave 1)
10002_ritsu_subscriptions.sql      (project Wave 2)
```

### Schema inheritance

Project tables inherit Bài #13 convention (4-col + audit) automatically:

```sql
-- 10001_ritsu_lessons.sql
CREATE TABLE lessons (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  -- domain-specific fields
  topic           text NOT NULL,
  difficulty      text NOT NULL,
  
  -- Bài #13 standardized state columns
  state           text NOT NULL DEFAULT 'draft',
  state_since     timestamptz NOT NULL DEFAULT now(),
  state_payload   jsonb,
  state_version   text NOT NULL DEFAULT '1.0.0',
  
  CONSTRAINT lessons_state_valid CHECK (
    state IN ('draft', 'published', 'in_progress', 'completed', 'archived')
  )
);

-- Reuse boilerplate state-since trigger
CREATE TRIGGER trg_lessons_state_since
  BEFORE UPDATE ON lessons
  FOR EACH ROW
  EXECUTE FUNCTION ops.touch_state_since();
```

## 32.4 Bootstrap automation: the 9-step pipeline

`bootstrap-new-project.sh` thực hiện 9 steps:

1. **Folder structure** — 10 pillar folders + frontend + supabase + wiki + runtime + .archives + raw + _build + notes + .claude + .scripts + .github + .husky + knowledge/schemas
2. **Charter templates** — process `charter.template.md`, `brand_voice.template.md`, `founder-profile.template.md` với 14 placeholders
3. **Tier 1 templates** — process all 19 `*.template.yaml` files
4. **Infrastructure files** — copy bootstrap.sh, validate-tier1.js, husky pre-commit, GitHub workflows
5. **Migrations** — copy 10 generic migrations to `supabase/migrations/`
6. **JSON Schemas** — copy 18 schemas to `knowledge/schemas/`
7. **Pillar READMEs** — process 7 pillar template READMEs
8. **Project metadata** — generate `agent-os.config.yaml`, `README.md`, `.env.example`
9. **Git init** — initial commit with metadata

Total time: ~3 seconds. Output: 100+ files ready for Wave 1.

## 32.6 Pillar discipline

### Naming convention: `XX-pillar-name/`

- `XX` = 2-digit prefix (00-99)
- `pillar-name` = lowercase, hyphenated
- Sortable in file explorer (alphabetical = natural order)

### Reserved prefixes

| Prefix | Usage | Mandatory? |
|---|---|---|
| 00 | charter (identity, vision, brand voice) | ✅ Always |
| 05 | ai-ops (skills, adapters, agents) | ✅ Always |
| 01-04 | front-of-house pillars (growth, customer, product, content) | ✅ Most projects |
| 06-08 | back-of-house (finance, compliance, integrations) | ✅ Most projects |
| 09+ | project-specific (e.g., 09-research for academic project) | Optional |

### Each pillar contains

```
XX-pillar-name/
├── README.md              ← scope, dependencies, Wave plan
├── sops/                   ← SOP folders (per Bài #9)
│   └── SOP-PREFIX-XXX-name/
│       ├── flow.yaml
│       ├── steps/
│       ├── tests/
│       └── README.md
└── agents/                 ← agent definitions (per Bài #5)
    └── agent-name.md
```

Some pillars omit `agents/` if they don't have specialized agents (e.g., 06-finance, 07-compliance).

### SOP naming convention

```
SOP-{PILLAR}-{XXX}-{slug}/
```

Examples:
- `SOP-GROWTH-001-content-publishing-cross-surface/`
- `SOP-CUSTOMER-004-account-deletion-gdpr/`
- `SOP-COMPLIANCE-001-gdpr-deletion/`
- `SOP-INT-001-webhook-stripe-process/`

Pillar prefix shortcuts:
- GROWTH, CUSTOMER, PRODUCT, CONTENT
- AI-OPS, FINANCE, COMPLIANCE
- INT (integrations — short enough)

## 32.10 Recommendation cho founder

### Maturity progression

| Level | Repo state | What to do |
|---|---|---|
| 0 | v2.6 architecture-only | Read playbook, understand patterns |
| 1 | v2.7 with migrations + schemas | Run bootstrap, customize charter, push to Supabase |
| 2 | Wave 1 in progress | Implement first SOPs, populate Tier 1 YAML |
| 3 | Wave 1 stable | Document boilerplate patterns observed |
| 4 | 2nd project starts | Tách boilerplate (per chương 31) |

### Anti-patterns to avoid

1. **Modifying generic migrations.** Edits go in 1xxxx_ range. Generic migrations (00001-00010) are upstream — modifications break boilerplate sync.

2. **Skipping JSON Schema validation.** Without strict validation, Tier 1 YAML drift là silent killer. Run validate before every commit.

3. **Ignoring pillar structure.** "01-business" hoặc "01-go-to-market" instead of "01-growth" → loses cross-project consistency.

4. **Mixing concerns across pillars.** Customer support belongs in 02-customer, NOT 01-growth. Don't blur boundaries.

5. **Inventing new pillar prefixes carelessly.** 09+ reserved, but adding 09-research randomly without thought → confuses operators.
