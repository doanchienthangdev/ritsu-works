## 33.3 8-Phase CLA Workflow

```
┌──────────────────────────────────────────────────────────────────┐
│  Phase 1: Problem Framing       (30 min, HITL: A)                │
│  Phase 2: Domain Deep-Dive      (60 min, HITL: A)                │
│  Phase 3: System Inventory      (30 min, HITL: A)                │
│  Phase 4: Options Generation    (90 min, HITL: B founder picks)  │
│  Phase 5: Architecture Design   (120 min, HITL: C critical)      │
│  Phase 6: Sprint Planning       (45 min, HITL: B)                │
│  Phase 7: Implementation        (1-4 weeks, HITL: B per PR)      │
│  Phase 8: Catalog Update        (30 min, HITL: A)                │
└──────────────────────────────────────────────────────────────────┘
```

**Pre-implementation total:** ~6h founder time (Phases 1-6)
**Implementation:** 1-4 weeks (Phase 7)
**Wrap-up:** ~30 min (Phase 8)

### Why 8 phases?

Each phase = decision gate hoặc artifact production. Compressing phases = quality loss:

- **Skip Phase 1 (Framing):** Architect from ambiguous problem → wrong solution
- **Skip Phase 2 (Domain):** Miss industry context → reinvent suboptimally
- **Skip Phase 3 (Inventory):** Duplicate existing capabilities
- **Skip Phase 4 (Options):** Pick first idea without comparison
- **Skip Phase 5 (Architecture):** No canonical spec → drift during build
- **Skip Phase 6 (Sprints):** No acceptance criteria → unclear when done
- **Skip Phase 7 (Implementation):** Just spec, no working capability
- **Skip Phase 8 (Catalog):** Lessons lost, no boilerplate extraction

Each phase blocks until prior complete (failure-handling rules).

### 33.5.4 Resume semantics

`/cla resume <id>` đảm bảo multi-session:

1. Read `ops.capability_runs WHERE capability_id = <id>` cho current state
2. **Re-run Phase 0 drift check** — state có thể đổi từ last session
3. Validate `.archives/cla/<id>/` folder + draft consistency
4. **Jump tới first incomplete phase** (per `phases_completed` array)
5. Nếu `main` thay đổi đáng kể từ Phase 5 drafts → warn + offer re-run Phase 5
6. Nếu `state_since > 7 days` → prompt staleness check

### 33.6.2 Common pre-flight (5 evolution sub-flows)

Trước mọi sub-flow:

1. **Drift gate**: `pnpm check` clean. Else ABORT.
2. **Lock acquire** (atomic): call `ops.capability_acquire_update_lock(<id>, <session_id>)`:
   - NULL return → `LockHeld` error với held-by + age. Founder wait hoặc `/cla force-unlock <id>`.
   - UUID return → lock acquired; proceed.
3. **State check**: capability phải `state IN ('operating', 'deployed')`. Else ABORT.
4. **INSERT NEW row** vào `ops.capability_runs`:
   - `capability_id = <id>` (same parent — multiple rows per capability)
   - `state='implementing', current_phase=1`
   - `supersedes_id = <prior row id>` (lineage chain)
   - `state_payload = {update_mode: 'fix|extend|revise|tune|deprecate', session_id: ..., parent_version: 'X.Y.Z'}`
   - `update_lock_session_id`, `update_lock_acquired_at` set by acquire
5. **Skill invocation** với `mode` parameter via state_payload.

### 33.6.3 `/cla fix <id>` — bug fix (HITL B, ~30 phút, ~$0.50)

## 33.15 Failure modes & guards

### Failure mode 1: Skip Phase 4 (Options)

**Detection:** `spec.md` exists without `options.md`
**Response:** Block Phase 5. Force regenerate Phase 4.

### Failure mode 2: Skip Phase 5 Tier C HITL

**Detection:** spec.md exists without `hitl_phase_5_run_id`
**Response:** Block Phase 6. Require explicit founder Tier C approval.

### Failure mode 3: Phase 7 session lost

**Detection:** `state = implementing` + last `capability_phase_events` > 7 days ago
**Response:** Resume from last completed sprint. Notify founder.

### Failure mode 4: Phase 8 skipped

**Detection:** `state = deployed` without `retrospective_path`
**Response:** Block transition to `operating`. Require retrospective.

### Failure mode 5: Cost overrun

**Detection:** `actual_cost_recurring_usd > estimated_cost_recurring_usd × 1.5`
**Response:** Alert (Bài #10), require founder review before continuing.

## 33.16 Operating mode (post-Phase 8)

After Phase 8 completes, capability state = `operating`:

### Continuous monitoring
- KPIs tracked in `ops.kpi_snapshots`
- Alerts active (per `alert-rules.yaml`)
- Dashboard page renders `v_capability_pipeline` view

### Periodic review
- Weekly: KPI trends
- Monthly: cost-bucket review (Bài #7)
- Quarterly: capability still relevant?

### Re-evaluation triggers
- KPI drift > 20% from target
- Cost overrun > 50% of estimate
- Founder time burden > 2x estimate
- New capability supersedes this one

When superseded:
- Mark old: `state = superseded`, `superseded_by_id = <new>`
- Old continues operating until new fully deployed
- Decommission per rollback plan in spec.md

## 33.21 Anti-patterns

### ❌ Skipping CLA cho "small" capabilities
Even small capabilities benefit from 8 phases (compressed timing). Skipping = ad-hoc reinvention.

### ❌ Phase 5 without Tier C HITL
Architecture decisions are usually irreversible. Tier C HITL = safety check. Bypassing = expensive rollback risk.

### ❌ Treating CLA as one-shot
CLA iterates Agent OS. Each capability adds skills, SOPs, integrations. Architecture evolves cumulatively.

### ❌ Skipping retrospective (Phase 8)
Lessons not captured = repeated mistakes across capabilities.

### ❌ Modifying spec.md after Phase 5 approval
Spec is canonical contract. Modifications require new HITL Tier C round.

### ❌ Multiple "active" capabilities với same slug
Use `superseded_by_id` lineage. Don't bypass uniqueness constraint.
