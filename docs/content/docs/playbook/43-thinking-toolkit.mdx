## 42.3 The 6 skills — what each does, when to use, when to skip

### 42.3.1 pyramid-principle-output (flagship)

> Top-line first; reader stops at any level; supporting points MECE; SCQA opener for long docs.

Founder reads 30-60s per output → with pyramid → 5-10s. Compound across thousands of invocations = single highest-leverage skill in the toolkit. Mandatory for 4 C-suite personas.

**When to use:** Any agent output ≥ 3 sentences; all C-suite persona output; morning brief; weekly review.

**When NOT to use:** Single-line factual answers; tool-output dumps; conversational acknowledgments; exploratory brainstorming where order = meaning.

### 42.3.2 so-what-test

> Every conclusion survives 2× "so what?": first reveals meaning, second reveals action. Fail either, drop or rework.

Forcing function against decoration. "MRR is $50K" — so what? Means at growth trajectory of X. So what (action)? Raise prices, OR double down on top channel.

**When to use:** Every supporting point in pyramid; every metric statement; final check before send.

**When NOT to use:** Pure factual lookups; raw tool output; questions (so-what tests answers, not questions).

### 42.3.3 tosca-problem-framing

> 5-dimension problem definition: Trouble, Owner, Success criteria, Constraints, Actors. Force structured framing BEFORE solutioning.

Most consulting work fails because problem defined wrong. Same for AI agents jumping to solutions on vague framings.

**When to use:** /cla problem-framer Phase 1 (mandatory); start of any analysis on ambiguous problem; debug session unclear root cause.

**When NOT to use:** Already crisp problem; operational lookups; trivial decisions.

### 42.3.4 mece-decomposition-check

> 2-test quality gate: Overlap test + Exhaustive test. Apply to any 3+ item list.

Most business lists fail MECE silently — "students, professionals, learners" overlap heavily. MECE catches structural failures before they propagate into analysis.

**When to use:** Pyramid supporting points (mandatory pair); customer segmentation; root-cause branches; any list claiming to "cover" a topic.

**When NOT to use:** Ordered sequences; intentionally exploratory; tag-style multi-membership; fuzzy categories by design.

### 42.3.5 2x2-synthesis-matrix

> When 4+ options need synthesis, two orthogonal axes reveal pattern that flat lists hide. BCG 1970, generalized by McKinsey/Bain.

Forces choosing the 2 most discriminating dimensions — discipline itself surfaces what really matters. Quadrant insights typically missed in flat lists.

**When to use:** 4+ candidates needing decision; feature prioritization (impact × effort); channel ROI; customer-segment value.

**When NOT to use:** 2-3 items (small table); single-dim ordering; correlated axes (matrix collapses to diagonal).

### 42.3.6 driver-tree-decomposition

> Decompose target metric → upstream actionable drivers. Each leaf marked 🟢 (direct influence) / 🟡 (indirect) / 🔴 (hard).

Fixes the "10-metrics pillar has 80+ KPIs but driver chains implicit" gap. When KPI drifts, formal trace from symptom → cause.

**When to use:** 10-metrics pillar work; cost-optimization-review weekly; KPI drift root-cause; growth planning ("how do we get to X?").

**When NOT to use:** Single-driver metrics; qualitative outcomes; opaque-driver metrics (third-party platforms).

## 42.6 Anti-patterns to watch

Patterns to AVOID when invoking thinking-toolkit:

1. **Over-application of pyramid on 1-line outputs** — "MRR is $0. Three supporting points..." adds noise. The fact IS the answer. Pyramid is for non-trivial output, not every utterance.

2. **MECE-force-fitting inherently overlapping categories** — Customer can be both "high-value" AND "high-risk". Use 2x2-synthesis-matrix instead; it allows overlap by design.

3. **2x2 with correlated axes** — Reach × engagement on social media are anti-correlated; matrix collapses to diagonal, no insight. Pick TRULY orthogonal dimensions.

4. **Driver tree without reaching actionable leaves** — "User satisfaction → Product quality → Features" doesn't reach intervention points. Either go deeper to measurable+actionable leaves, OR abandon driver tree for this metric.

5. **TOSCA every question** — Heavyweight tool. Use only when genuinely ambiguous (5+ min friction to scope). Crisp questions skip TOSCA entirely.

6. **So-what on questions** — So-what tests answers, not questions. "What's our MRR?" is not a conclusion to test.

## 42.7 Bài học từ ship — lessons for future capability work

### 42.7.1 Single-session autonomous is feasible for SCOPE-BOUNDED capabilities

This capability shipped in ~5h overnight autonomous because:
- Scope was BOUNDED (6 specific skills, no infrastructure changes)
- Founder pre-authorized comprehensively
- All 8 phases of /cla collapsed into compressed execution
- Reuse ratio ~70% (docs-engine adapters, resolver catalog, capability-registry pattern, persona file structure)

**Counter-example:** capabilities like /update (8 PRs, multiple sprints) or gbrain (Sprint 2 capability journey across multiple sessions) cannot single-session because they touch infrastructure (new DB tables, new MCP servers, new commands).

**Heuristic:** if reuse ratio > 60% AND no infrastructure changes AND scope ≤ 8 files → candidate for single-session ship.

### 42.7.2 Founder standing-authorization is structural shortcut for Tier C compression

Normal /cla propose has 3-4 Tier C HITL gates (Phase 4 options, Phase 5 architecture spec, Phase 8 promotion). Each gate normally requires Telegram approval ceremony.

For SCOPE-BOUNDED capabilities with comprehensive founder pre-auth at session start, these gates can be:
- Captured in internal Muse panel synthesis (Phase 5)
- Documented in PR description (founder reviews post-merge if desired)
- Audit-trailed via ops.capability_runs + ops.decisions

This is NOT a way to bypass HITL — it's compressing HITL ceremony when founder has explicitly authorized a scoped batch. D-MAX actions (Product Supabase, governance edits, secrets) remain forbidden regardless of session authorization.

### 42.7.3 Skill quality > Skill quantity

The /muse + gstack tradition is dozens of personas/skills. Thinking-toolkit shipped only 6 skills, with explicit 6-rejected list explaining why we DID NOT add more.

Quality discipline:
- Each skill has 3 worked examples (good / anti-pattern / edge case)
- Each skill has when-NOT-to-use section to prevent over-application
- Each skill has composition notes (how it pairs with other thinking-toolkit skills)
- Each skill has anti-claims (what it does NOT claim to do)

This is the same quality bar applied to wiki-sync/distill, eval-evo skills, capability-lifecycle skills. Without this bar, skill-library bloats with overlapping near-duplicates that confuse rather than help.

### 42.7.4 Founder dogfooding accelerates capability adoption

Pyramid Principle output structure used in the very RESPONSE that founder approved the capability. Eat own dog food in the proposal itself. Persona output adoption thereafter is much easier when founder has SEEN the pattern in practice.

## 42.9.6 v1.2 extension — curated +5 skills (the "curate, don't inflate" answer)

2026-06-03. Founder asked the sharpest possible scaling question: *"implement TẤT CẢ các concepts phù hợp trong Cracked-It! + Bulletproof thành skills cho /think — ổn không?"* The answer — and the lesson — was **curate, don't inflate**. A skill carries a resolver-catalog + maintenance cost; most book concepts are *knowledge* (a noun you recall), not *operations* (a verb you run), and knowledge belongs in the wiki library, retrievable — not as 200 commands.

**The 5-test gate** (a concept becomes a `/think` skill only if it passes ALL): (1) operation-not-knowledge; (2) invoked-at-a-decision-point; (3) distinct from the existing skills + each other; (4) general/portable (not a book's domain example); (5) worth the catalog cost. Triaging all **259** distilled concepts: only **~2%** passed as new operations, ~28% were already in the 6, **~54% stay as wiki library**. Result — **+5 skills (6→11)**:

| Skill | Cognitive mode it adds |
|---|---|
| `hypothesis-driven` | sequence an analysis (falsify-first + one-day answer) |
| `pre-mortem` | surface risk before committing (prospective hindsight) |
| `root-cause` | trace a *confirmed* symptom backward (Five Whys, scoped) |
| `design-thinking` | *generate* when there's nothing to decompose (the one generative skill) |
| `debias` | guard the thinker (pre-commit bias checklist, wraps ~28 concepts) |

**Read-before-write caught 2 conflicts** — the payoff of reading the capability's own history before extending it:
1. v1.0 had *deliberately rejected* "5 Whys" — but for **framing** (Cracked it! p.58, *"asking why isn't always specific enough"*). `root-cause` re-admitted it NARROWLY for *causal-tracing of a confirmed symptom*; framing stays with TOSCA. The two source books genuinely disagree by design; v1.0 sided with Cracked it! for framing, v1.2 added back the Bulletproof use only.
2. The planned "pyramid += SCR/SCQA" enhancement was a **no-op** — `pyramid-principle-output` already exposed both Grouping + Argument/SCR variants. Dropped before writing.

Review: **@cto** FIX-FIRST (fixed dangling refs — `root-cause` cited a non-existent `debugger` agent; `debias` cited a non-existent `multiple-frameworks` skill) + **conceptual critic** SHIP-ALL-5 (all five survived a real cut-test). **Lesson:** the lever for thinking quality is NOT framework *count* (259 already exist in the wiki) — it's a *memorable* set of operations + applying the right one at the right moment. More frameworks past a point *reduces* quality (choice overload — which the books themselves warn against: `maslows-hammer`, `framework-mental-model-danger`).
