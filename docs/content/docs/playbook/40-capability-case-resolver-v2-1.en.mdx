## 40.6 What worked / lessons

### ✓ Worked

1. **Non-breaking incremental** — v2.0 architecture preserved entirely. Only generators + CATALOG_FILES + CLAUDE.md imports extended. All v2.0 tests still pass without modification.

2. **Composition output stays flat** — Resisted temptation to redesign output schema (`context_sources` vs `active_components` grouping). Wire format unchanged means consumer code (if any existed) wouldn't break.

3. **Generator pattern reusable** — Each new generator follows same 4-step pattern (walk → parse → extract → emit). Easy to add more kinds in v2.2 if needed (just add CONFIG entry + generator function + CATALOG_FILES line).

4. **Same-day iteration** — Spec → build → test → deploy → playbook → docs → merge all in \<2 hours. Wave 1 maturity proves out.

5. **Catalog content grows organically** — As `/wiki sync` adds sources, wiki catalog auto-grows. As new SOPs land, sop catalog grows. No manual curation needed.

### ✗ Didn't work / lessons

1. **First sop generator caught SOP-skeleton template** — `_templates/SOP-skeleton/` matched the SOP-* pattern. Required adding `_templates` and `.claude` to exclusion list in directory walker. **Lesson:** Recursive directory walkers need explicit "don't traverse" lists for templates, worktrees, and tool-internal folders.

2. **VALID_STATUSES too narrow** — v2.0 validator only accepted `[active, stub, deprecated, planned, deferred]`. Capability registry uses `operating, implementing, proposed` etc. Required expanding VALID_STATUSES to 12 values. **Lesson:** When catalog spans multiple source types (each with own status vocabulary), validator status enum must be union of all source vocabularies.

3. **Hook frontmatter inconsistent** — Some hooks have `type: PreToolUse`, others `event: pre`, others nothing. Generator fell back to "PreToolUse" default. **Lesson:** When extracting metadata from heterogeneous frontmatter, design fallback logic for missing fields rather than failing.

4. **One test became flaky after expansion** — `"the and is are the and is are"` stop-word-only trigger used to return `no_match`. After adding 134 SOP entries with varied descriptions, weak matches surface (still below dispatch threshold but enough for `surface_candidates`). Test updated to accept both outcomes with confidence ceiling check. **Lesson:** Tests that assume specific decision outcomes can become flaky when catalog volume changes; test thresholds and bounds instead of exact outcomes.

### 40.9.9 What worked / lessons v2.2

#### ✓ Worked

1. **Hybrid pattern (Option C) đúng** — distinct kinds cho internal categories đã thấy, meta-kind cho external. LLM filter dễ (only `metric` kinds when looking for KPIs); 3rd party expansion không cần thêm code (chỉ YAML entry).

2. **Skeleton-only adapter** — đủ để operator hiểu extension point sẽ ở đâu; không over-engineer runtime trước khi có consumer.

3. **Same-day compressed flow #2** — Phase 1-5 skipped vì architecture v2.1 đã sound. Phase 6-7-8 chạy thẳng trong 1 session. Wave 1 maturity proves out lần thứ hai.

4. **Per-persona workforce KPIs surface** — 23 KPIs phụ persona.ceo/cto/cgo/cpo originally chỉ visible trong YAML file. Sau v2.2 ambient catalog → @ceo / @cto session tự thấy KPI mình bị đánh giá.

5. **Secret defense-in-depth** — pages.md test enforces SECRETS.md / founder-profile.md exclusion; external-sources.yaml test enforces auth_env = env var NAME only. Cả hai catch regression nếu Tier 1 file structure đổi.

#### ✗ Didn't work / lessons

1. **Estimated 20 metrics, actual 83** — per-persona workforce KPIs (persona.ceo.routing_accuracy_first_try, etc.) đã được add trong PR 3/4 stack mà brainstorm không know about. **Lesson:** Khi count entries trong yaml registry, đọc actual file before estimating — đặc biệt khi registry chứa multi-tier data (baseline KPIs + workforce KPIs).

2. **Token cost +18K (+60%) cao hơn estimate (+13K)** — metrics size bị undercount. Still well within budget (~24% of 200K) nhưng signal: catalog growth cần track per-kind tokens trong test, không chỉ entry count.

3. **3 pre-existing tests updated reluctantly** — `errors.test.ts`, `catalog-loader.test.ts`, `integration.test.ts` hardcoded "11 kinds" / specific regex. Mỗi lần expand kinds phải edit 3 chỗ. **Lesson:** Test arrays nên import từ source-of-truth constants thay vì hardcode duplicate; integration regex nên test pattern abstractly.

4. **CI warn validator `governance/ROLES ↔ skills` vẫn fail (27 issues)** — pre-existing từ trước v2.2; ROLES.md reference 27 skills chưa implement (planned roles). Không phải v2.2 regression. **Lesson:** Warn-tier validator failures cần explicit `ack: <reason>` comment trong test output để distinguish "known pre-existing" vs "new regression".

### 40.9.11 Why this isn't a new chapter

Founder explicit request: *"Update bổ sung playbook và docs vào phần tiếp theo của Chapter 40 cho đỡ phải thêm chapter mới."*

Justification:
- **Architectural continuity** — v2.2 tiếp tục pattern "non-breaking incremental on sound architecture" mà v2.1 đã ship trong Chương 40 chính. Không có novel paradigm.
- **Same case study, same capability family** — `resolver-v2.x` family share spec, share engine, share audit table. Một chương = một capability case study.
- **Postscript pattern** — sau khi case study chính đóng (40.7 Wave 1 closing reflection), v2.2 demonstrates pattern integrity bằng cách incremental thêm lần nữa. Đó chính là evidence the pattern works.
- **Chương mới = thêm walkthrough cost** — operator phải scan thêm 1 entry sidebar, ToC dài thêm, PDF nặng thêm. Nếu content thực sự incremental → postscript section đủ.

**Rule of thumb (mới phát hiện qua v2.2):** Capability case study chỉ nên thêm chương mới khi (a) capability hoàn toàn mới (không phải iteration), HOẶC (b) iteration thay đổi architecture (paradigm shift như v1→v2). Same-architecture content expansion → postscript section.

Chương 40 vì thế trở thành **multi-version capability case study** — main chapter cho v2.1 (Wave 1 closing); postscript cho v2.2 (Wave 1 post-closing confirmation). Tương lai nếu v2.3 (lazy `record` kind) hay v2.4 (adapter runtime) cũng same-architecture → có thể tiếp tục append section 40.10, 40.11, etc.
