## 40.6 What worked / lessons

### ✓ Worked

1. **Non-breaking incremental** — v2.0 architecture preserved entirely. Only generators + CATALOG_FILES + CLAUDE.md imports extended. All v2.0 tests still pass without modification.

2. **Composition output stays flat** — Resisted temptation to redesign output schema (`context_sources` vs `active_components` grouping). Wire format unchanged means consumer code (if any existed) wouldn't break.

3. **Generator pattern reusable** — Each new generator follows same 4-step pattern (walk → parse → extract → emit). Easy to add more kinds in v2.2 if needed (just add CONFIG entry + generator function + CATALOG_FILES line).

4. **Same-day iteration** — Spec → build → test → deploy → playbook → docs → merge all in \<2 hours. Wave 1 maturity proves out.

5. **Catalog content grows organically** — As `/wiki sync` adds sources, wiki catalog auto-grows. As new SOPs land, sop catalog grows. No manual curation needed.

### ✗ Didn't work / lessons

1. **First sop generator caught SOP-skeleton template** — `_templates/SOP-skeleton/` matched the SOP-* pattern. Required adding `_templates` and `.claude` to exclusion list in directory walker. **Lesson:** Recursive directory walkers need explicit "don't traverse" lists for templates, worktrees, and tool-internal folders.

2. **VALID_STATUSES too narrow** — v2.0 validator only accepted `[active, stub, deprecated, planned, deferred]`. Capability registry uses `operating, implementing, proposed` etc. Required expanding VALID_STATUSES to 12 values. **Lesson:** When catalog spans multiple source types (each with own status vocabulary), validator status enum must be union of all source vocabularies.

3. **Hook frontmatter inconsistent** — Some hooks have `type: PreToolUse`, others `event: pre`, others nothing. Generator fell back to "PreToolUse" default. **Lesson:** When extracting metadata from heterogeneous frontmatter, design fallback logic for missing fields rather than failing.

4. **One test became flaky after expansion** — `"the and is are the and is are"` stop-word-only trigger used to return `no_match`. After adding 134 SOP entries with varied descriptions, weak matches surface (still below dispatch threshold but enough for `surface_candidates`). Test updated to accept both outcomes with confidence ceiling check. **Lesson:** Tests that assume specific decision outcomes can become flaky when catalog volume changes; test thresholds and bounds instead of exact outcomes.

### 40.10.1 Bài toán — v2.2 catalog token cost ceiling

Sau khi v2.2 land với 16 recipient kinds, ambient catalog total ~55K tokens (16 file × ~3.4K avg) — load mỗi session start qua 16 `@import` directives trong `CLAUDE.md`. Founder dùng vài tuần, phát hiện 2 cognitive issues:

1. **Context decay**: ở message 30+ trong session dài, model "quên" recipients có sẵn → fallback dùng raw Bash (grep, find) thay vì invoke skill chuẩn. Một bypass-detection log sau này confirms ~12% of "should-have-resolver-called" moments actually skipped resolver.
2. **Token budget pressure**: 55K ambient = 27.5% của 200K context window. Mỗi session paid before doing any work. Subagents inherit it. Scaling to 1500+ recipients (projected post-Wave 2) sẽ break.

> *"Tôi thấy nếu load hết thì quá tốn context và context decay... 1 resolving table đủ gọn như là 'bản đồ dắt túi đủ nhỏ gọn'."*

**Diagnostic:** "preload everything" trade-off đã đảo dấu. Đầu v2 nó OK (118 entries, ~16K). v2.1/v2.2 push lên 252/392 entries. v3 cần kiến trúc khác.

### 40.10.2 Inspiration — Claude Code's ToolSearch pattern

Khi brainstorm, founder + AI scan thiết kế Claude Code platform. Phát hiện: Anthropic giải quyết cùng bài toán với **2-tier architecture**:
- **Built-in tools** (Read, Write, Bash, Edit, ...) → loaded vào system prompt (ambient, lightweight)
- **Deferred tools** (MCP tools, extras) → chỉ NAME visible trong `<system-reminder>` (zero token cost cho schema); `ToolSearch` meta-tool fetch schema khi cần

**Pattern**: Lightweight ambient layer + heavyweight deferred drill-down. Battle-tested at scale ~50 tools. Decision: mirror pattern cho resolver, scale lên 386+ recipients.

### 40.10.3 Architecture — INDEX + JIT MCP

v3.0 design:

```
LAYER 1 (always-on)
─────────────────────
CLAUDE.md @import knowledge/recipients/INDEX.md  (~11K tokens)
└─ 386 active recipients × 1-line summary
└─ Path A/B discipline header
└─ Invoke conventions for 14 kinds

LAYER 2 (JIT, on-demand)
─────────────────────
mcp__supabase-ops__resolver_find(args)
└─ Pre-warmed catalog at MCP subprocess boot (~50ms)
└─ Keyword pre-filter → ~20 candidates
└─ Session-model ranking (NO API key — uses Claude Code subscription)
└─ Per-role filter
└─ Returns full when_to_use + composition graph + recency
└─ Audit → ops.resolver_decisions (mode='A2')
```

**Key data points:**
- 55K → 11K ambient (-80%)
- Path A `<` 1ms (direct invoke from 1-line)
- Path B 80-440ms (drill-down via MCP)
- 0 API cost (session model ranking, policy-aligned)
- 386 active / ~614 total recipients (stubs hidden)
- 65 tests, 13 validators, 1 migration (00038 adds 'A2' to mode enum)

### 40.10.4 Policy-enforcement story — iter4 revision

v3 spec went through 4 iterations. Iter1-3 designed L3 ranking với Haiku-via-API-key inside MCP subprocess. **Iter4 founder critique:**

> *"Ritsu-works hoạt đông trong môi trường Claude Code/Codex thuê bao subscription, những tác vụ như Haiku rank là dùng API Key phải không? Nếu phải thì tại sao không dùng ngay trong môi trường luôn? Hạn chế API Key khi thật cần thiết mới dùng."*

→ Violation of `external-source/anthropic-api` policy: "In-session Claude Code calls do NOT need API key — use host session's billing."

**Architectural revision:** Move L3 ranking from Haiku-in-MCP → session-model-in-Claude-Code. MCP returns 20 keyword-filtered candidates; session model (Opus/Sonnet) does the ranking inline. Result: $0 API cost, ~89% recall (Opus `>` Haiku at 20-candidate ranking), policy-aligned, simpler code (-200 LOC). Spec status revised iter3 → iter4 → READY.

**Lesson:** policy compliance is generative constraint. The "obvious" architecture (call Haiku from MCP subprocess) violated policy. Forcing the constraint produced a SIMPLER architecture (no API client, no cost tracking, no budget cap, no failure mode for API rate limit).
