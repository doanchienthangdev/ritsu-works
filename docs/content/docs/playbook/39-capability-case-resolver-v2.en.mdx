## 39.3 Architecture v2 — 3 consumer modes leveraging ambient LLM

```
Layer 1 — Catalog (5 markdown files, single source of truth)
  knowledge/recipients/
    ├── skills.md      71 entries  (post-cleanup: 67 entries)
    ├── commands.md    12 entries
    ├── agents.md      5 entries
    ├── personas.md    21 entries
    └── mcps.md        9 entries
  118 entries / ~16K tokens = 8% of 200K context window

Layer 2 — Consumer modes
  Mode A: In-session ambient   90%+ usage  $0/query, 0ms
  Mode B: Explicit /resolver    9% usage    $0/query (in-session), ~5ms
  Mode C: Keyword fallback      1% usage    $0/query, <5ms (CRON/edge fn)

Layer 3 — Engine modules (~600 LOC vs v1's 1832 LOC, -67%)
  scripts/resolver-v2/
    ├── catalog-loader.cjs       parse recipients/*.md → in-memory index
    ├── keyword-fallback.cjs     ~200 LOC Mode C matcher (same catalog source)
    ├── sync.cjs                 frontmatter → catalog (dry-run default)
    ├── audit.cjs                buildRecord + writeRecord (insertFn DI)
    ├── errors.cjs               14 typed exception classes
    └── catalog-generator.cjs    one-shot generator for sync

Layer 4 — Validators (4 new, replacing 4 v1 validators)
  scripts/cross-tier/
    ├── validate-resolver-v2-schema.cjs
    ├── validate-resolver-v2-uniqueness.cjs
    ├── validate-resolver-v2-coverage.cjs
    └── validate-resolver-v2-link-integrity.cjs
  All 4 registered trong scripts/check-consistency.cjs

Layer 5 — Audit table extended (migration 00035, additive ADD COLUMN)
  ops.resolver_decisions
    + llm_reasoning text             — Mode B LLM rationale
    + mode char(1)                   — 'A' | 'B' | 'C'
    + catalog_files_loaded text[]    — which recipients/*.md contributed
    + composition_supporting text[]  — supporting recipient IDs
```

### Mode A pattern (PRIMARY, 90%+ usage)

`.claude/CLAUDE.md` auto-imports catalog via `@knowledge/recipients/*.md`. Every Claude Code session has catalog trong ambient context.

Khi agent/skill cần resolve trigger:
1. Reasons naturally (no special "resolver call")
2. Identifies primary + supporting recipients from ambient catalog
3. Invokes recipient directly (`Skill({...})`, `Agent({...})`, etc.)
4. Optionally writes audit row for significant decisions

**Latency:** 0ms additional (catalog already loaded).  
**Cost:** $0 (no extra LLM call; recall happens during normal reasoning).

### Mode B pattern (Explicit, audit/debug)

```bash
/resolver query "onboard first 30 customers"
```

Skill executes:
1. Load catalog files (cached by mtime)
2. Format structured prompt với catalog + trigger
3. Current session LLM reasons → emits JSON `{primary, supporting[], rationale, alternatives[]}`
4. Validate IDs exist trong catalog (reject hallucinations via `HallucinatedRecipient` error)
5. Build audit record với `mode='B', llm_reasoning=<rationale>, composition_supporting=[...]`
6. Write audit qua `mcp__supabase-ops__insert`
7. Return human-readable output

### Mode C pattern (Keyword fallback, CRON/edge fn)

No LLM in loop. `scripts/resolver-v2/keyword-fallback.cjs` reads SAME catalog files:

```bash
node -e "
const { match } = require('./scripts/resolver-v2/keyword-fallback.cjs');
const r = match({ trigger: 'sync wiki' });
console.log(r.matched?.recipient?.id, 'conf=' + r.matched?.confidence);
// → command/wiki conf=0.95
"
```

Recall acknowledged ~30% (vs Mode A's 80%+); use cases: CRON jobs, pre-commit hooks, Edge Functions.

## 39.4 Catalog format — what founder + LLM both read

Each recipient = one `##` section trong file kind tương ứng:

```markdown
## skill/customer-onboarding

**Kind:** skill
**When to use:** Onboarding a new paying customer (especially the first 30 high-touch
Zoom onboardings). Also when scripting reusable customer onboarding flows.
**Invoke:** `Skill({ skill: "customer-onboarding" })`
**Composes with:**
- persona/cs-coach
- mcp/supabase-ops__insert
**Role scope:** founder, cs-coach, customer-lead
**Status:** active
**Pillar:** 05-customer/success
```

Required fields: id (heading), Kind, When to use, Invoke, Status  
Optional fields: Composes with, Role scope, Pillar, Aliases, Disambiguator

**Tại sao MDX format thay vì YAML:**
- Human + AI both read it naturally — không cần parser
- "When to use" là natural language → LLM hiểu intent
- "Composes with" hiện composition explicit
- 1 file = 1 markdown doc loadable as attachment

## 39.7 What worked / what didn't

### ✓ Worked

1. **Same-day rewrite ceremony** — v1 ship → critique → v2 design → v2 ship trong \<8h. Wave 1 maturity enabled this.

2. **LLM-native catalog** — Mode A's "ambient catalog + natural reasoning" replaces keyword-matching paradigm entirely. Zero performance regression because no extra LLM call.

3. **Single source of truth** — `recipients/*.md` eliminates v1's 3-way drift risk (routes/+overrides/+adapters/). One catalog feeds all 3 modes.

4. **Auto-generated catalog từ frontmatter** — Sync script walks source SKILL.md/command.md/agent.md/PERSONA.md/mcp-tools.yaml và emits MDX. Founder doesn't hand-craft trigger keywords.

5. **5-phase test methodology applied rigorously** — 215 tests catch real bugs (5 found during initial run, all fixed):
   - `InvalidKindFilter.kind` property name collision với parent class field
   - `extractFirstParagraph` only stripped H1, not H2+
   - `audit.writeRecord` returned `undefined` instead of `null` on empty result
   - Stop-word filter "you" passes (3 chars) — test expectation wrong
   - Persona description fallback "## Identity" (extractFirstParagraph bug)

6. **Composition output là free** — Vì LLM trả về `{primary, supporting[], rationale}` natively, không cần code composition layer riêng. v1 spec mentioned `composition.plan` (CP-2) but never implemented because would have required dedicated engine logic. v2 gets it for free.

7. **Audit ADD-COLUMN migration non-destructive** — v1 row preserved (`run_id=794cdaf5`), backfilled to `mode='B'`. Single migration applies + tests + smoke verify.

### ✗ Didn't work / lessons

1. **First catalog generation had stale entries** — Generated catalog BEFORE deleting v1 skills/resolver/ subdirectory. Catalog included `skill/resolver/orchestrator` etc. Required regeneration after cleanup. **Lesson:** Catalog generation must be POST any source deletions.

2. **Duplicate persona IDs** — First generator passed walked PERSONA.md + agent.md + command.md etc. tất cả under workforce-personas/\<persona>/ → generated multiple entries với same slug. Fixed via `pattern: /\/PERSONA\.md$/` filter. **Lesson:** Multi-file-per-entity directories need explicit file selection.

3. **Persona description from PERSONA.md body was "## Identity"** — `extractFirstParagraph` only stripped first H1, leaving "## Identity" heading as the "first paragraph". Fixed by stripping ALL leading headings. **Lesson:** Markdown body extraction needs multi-heading-skip logic.

4. **Auto-classifier blocked migration apply** — `supabase db push --include-all` blocked by Production Read classifier ("Blind Apply without explicit user authorization"). Resolved by `AskUserQuestion` with explicit migration name + 3-option choice. **Lesson:** Production DDL apply requires per-migration consent ceremony, regardless of broader project authorization.

5. **MCP tool registration deferred** — v1 spec promised `mcp__resolver__query` MCP tool, never registered trong `knowledge/mcp-tools.yaml`. v2 inherits this gap. Consumers needing MCP transport use `Skill({skill: "resolver-query"})` instead. **Future:** Add MCP wrapper trong v2.1 if real consumers emerge.

## 39.8 Lessons for future capabilities

### Lesson 1: Dogfood signal trumps spec rigor

v1 spec was thoroughly reviewed (Sprint 1-4 plan, 4 STOP gates, architect outside-voice challenge). All quality gates passed. v1 STILL had architectural paradigm mismatch — discoverable only via real usage.

**Pattern:** Ship MVP fast → dogfood → critique → potentially same-day rewrite. Don't over-invest in upfront design for first iteration.

### Lesson 2: Compression ceremony works post-Wave 1

CLA Phases 1-5 collapsed to ~1 hour when:
- Founder has clear intuition (validated by dogfood)
- Domain already understood (no new pillar)
- Wave 1 patterns established (file structure, audit table, validators)

**Anti-pattern:** Don't try compression for greenfield capability in unfamiliar domain.

### Lesson 3: LLM-native > custom matching engine for trigger lookup

If task category is "given natural language query → find related X in finite catalog", LLM-in-context loop beats custom search engine for:
- Recall (handles synonyms, NL phrasing, typos)
- Composition (returns assembled tool list naturally)
- Code volume (massive reduction)
- Curation labor (NL description vs keyword crafting)

Trade-off: 15K tokens ambient cost per session. Worth it when caller is ALREADY an LLM (Claude Code session).

**Generalizable to:** runbook lookup, persona discovery, troubleshooting decision trees, KB search.

### Lesson 4: Capability lifecycle = capability case study

Wave 1 ship cadence (Chương 34-39: wiki-sync, docs-engine, core-redesign, /evolve, /resolver v1, /resolver v2) demonstrates Bài #20 framework's value: each capability ship produces:
- Code + tests + spec (the deliverable)
- Playbook chapter (the case study)
- Retrospective (the lessons)
- Validator + drift gate (the protection)

This Wave 1 cycle = **6 capabilities trong ~10 ngày**. Resolver v1 → v2 same-day = velocity ceiling demonstration.

### Lesson 5: Founder critique is the highest-value signal

v1 → v2 rewrite triggered by ONE founder question: *"Bản chất thực sự của resolver engine là gì?"*. AI assistant's job: take critique seriously, score honestly, articulate trade-offs, recommend decisively.

**Anti-pattern:** Defend v1 architecture because "we just shipped it". v1 is sunk cost; v2 quality is what matters.
