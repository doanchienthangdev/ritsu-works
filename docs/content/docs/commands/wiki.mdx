Project-scoped command for ritsu-works. Front-end for the wiki-sync capability
(`wiki-sync-from-refs`). Thin orchestrator — phase logic lives in the skills
under `06-ai-ops/skills/wiki-sync/`. Follows the same orchestrator pattern as
`/cla` (delegate to skill; manage HITL gates; persist state).

**v3.0 (2026-05-18 onward): DEFAULT semantic = distill+extract.** Source files
become RECORD pages; important knowledge (concept / observation / decision / idea)
is LLM-extracted into separately-projected `wiki/<type>/<slug>.md` entity pages
with citation via `ops.knowledge_extractions`. `--verbatim` flag falls through
to v2.0 verbatim-projection behavior.

**v4.0 (Sprint 1 of v4 revise, 2026-05-18): source-grouped LAYOUT.** Source RECORD
lands at `wiki/<source-slug>/source.md`; derived entities at
`wiki/<source-slug>/{concepts,observations,decisions,ideas}/<entity-slug>.md`
(composite UNIQUE within source). Per-book chapters at
`wiki/<book-slug>/chapters/chapter-NN.md`. Skills can specify
`input = wiki/<source-slug>/` as a coherent input package. Reverse-lookup
link-lists at `wiki/_index/<page_type>/<canonical-name>.md` (Sprint 2;
regenerated by `index-rebuild` skill, excluded from `/wiki audit` orphan checks).

## Workflow

### `/wiki sync <path>`

1. **Detect adapter** — read `<path>`:
   - If directory → `folder-adapter` (v4.1: BFS-recursive bounded by `--depth=d` default 3, `--max-nodes=N` default 20. v4.2: output nests under `wiki/<namespace>/`, where namespace = `--out=<name>` flag or slugified input basename + `-N` suffix if conflict).
   - Else extension / URL pattern → one of the 5 file adapters in `knowledge/ingestion-sources.yaml`
   - Bail with helpful error if no adapter matches
2. **Chapter-split prompt** — if PDF > 100 pages OR `--split` flag passed, run `chapter-splitter` skill which uses `AskUserQuestion` to confirm split mode (`toc` / `count=N` / `heading=h2`). Children get their own `ingestion_jobs` rows with `parent_job_id` (migration 00030 Block C).
3. **Acquire lock** — `SELECT ops.wiki_sync_lock(<entity_type>, <slug>)` (migration 00027) to prevent concurrent writes.
4. **Dedup check** — compute `source_hash = sha256(ref_content)`; query `ops.ingestion_jobs WHERE source_hash = ? AND state IN ('completed')`. If exists and `--force` not set, return "ref unchanged; wiki up-to-date".
5. **Run SOP-INGEST-001** — invokes the 6-step pipeline skill via `06-ai-ops/sops/SOP-INGEST-001-wiki-sync/`. For markdown + folder paths, prefer the CLI helper `scripts/wiki-sync/ingest.cjs` (v2.0 PR3) for deterministic file-side steps; LLM-touching steps stay in this command's session.
6. **Confirm to founder** — print summary (entity type, slug, page count, cost) + link to written wiki path. For folder ingest, also prints the per-file summary table.

### `/wiki get` — 3 modes (v4.3 + v4.4)

Extract bundled context from a wiki source-grouped package. Output suitable for piping to another command's prompt OR writing to file via `--to=<path>`.

**Mode 1: Spec mode** (v4.3) — pure filesystem read + assemble, $0 cost.
**Mode 2: Query mode** (v4.4 NEW) — semantic retrieval via MCP `wiki_ask` → entity list → bundle.
**Mode 3: Entity-list mode** (v4.4 NEW) — explicit slug list → bundle. Used by Mode 2 internally; also direct ad-hoc use.

#### Mode 1: Spec mode

**Source spec grammar:**

| Spec | Resolves to |
|---|---|
| `<source-slug>` | Full source: source.md frontmatter + all chapters + all entities (capped by `--max-entities`) |
| `<source-slug>/chapter-N` | Chapter N file + all entities with frontmatter `source_chapter_index: N` |
| `<source-slug>/chapter-NN-<slug>` | Specific chapter file (full filename) + entities citing it |
| `<source-slug>/<type>` | All entities of type (concepts \| observations \| decisions \| ideas) |
| `<source-slug>/<type>/<entity-slug>` | One entity page (full body + frontmatter optional) |

**Workflow:**

1. **Parse spec** — split by `/`; resolve source dir; bail if not v4.0 source package (no `source.md`).
2. **Collect chapters** — based on scope.
3. **Collect entities** — filter by frontmatter `source_chapter_index` (for chapter-N spec) or by file path.
4. **Assemble bundle** — header (spec + source metadata) + inventory + source RECORD frontmatter + chapter bodies + entity bodies + provenance footer.
5. **Output** — write to `--to=<path>` (creates parent dirs) OR stdout. Summary line to stderr.

**Output format**: Markdown bundle starting with `<!-- wiki-context-bundle generated by /wiki get v4.3 -->` + structured H1/H2/H3 sections. Every entity carries provenance (file path, chapter index, confidence, review state). Footer reminds operator NOT to edit bundle directly.

**Cap default**: 100 entities per bundle (over-cap reported as `dropped` count). Increase via `--max-entities=N`.

**Flags:**

- `--src=<spec>` REQUIRED. The source spec.
- `--to=<path>` Optional. Output file path (relative to repo root or absolute). Without it, prints to stdout.
- `--summary` Compact mode: chapters → outline only; entities → first paragraph only.
- `--include-frontmatter` Include entity YAML frontmatter in output (default: stripped, only key metadata in header).
- `--max-entities=<N>` Cap on entity count (default 100). Drops are reported.

**Examples:**

- `/wiki get --src=marketing-management-kotler/chapter-14` — print Kotler MM Ch 14 + 8 entities to stdout
- `/wiki get --src=marketing-management-kotler/chapter-19 --to=.archives/cla/<id>/ch19-context.md` — bundle to file for `/cla propose` reuse
- `/wiki get --src=principles-of-marketing-kotler --summary --max-entities=20` — high-level outline of entire book
- `/wiki get --src=marketing-management-kotler/decisions/decision-ritsu-direct-marketing-engine-email-lifecycle` — single decision entity full body

**Cost**: $0 (no LLM call; pure filesystem read).

**Composition pattern**: paste output (or read from `--to=<path>` file) into the next command's prompt. The bundle's citation chain is preserved via frontmatter excerpts.

#### Mode 2: Query mode (v4.4 NEW)

Semantic retrieval bundle. Invoked when `/wiki get` includes `--query=<text>` flag.

**Workflow:**

1. Orchestrator (Claude Code session) calls `mcp__supabase-ops__wiki_ask` with the query.
2. If `--src=<source>` is also given, pass `filter.source=<source>` to scope retrieval to that package.
3. MCP returns up to 15 entity slugs ranked by similarity. If `no_coverage` (e.g. embeddings backfill not yet complete), orchestrator falls back to filesystem keyword match on entity slugs + titles.
4. Orchestrator builds entity CSV: `<source>/<type>/<slug>` per result.
5. Orchestrator invokes `scripts/wiki-sync/get.cjs --entities=<csv> --query-context-header="<query>" [--src=<source>] [--to=<path>]`.
6. Bundle header annotates **Query**: original `<text>` so the bundle self-documents what query produced it.

**Cost**: $0–$0.01 (MCP embedding call only; bundle assembly is filesystem).

**Examples:**

- `/wiki get --query="customer segmentation strategies" --src=principles-of-marketing-kotler --to=.archives/cla/<id>/segmentation.md` — segmentation entities scoped to one book
- `/wiki get --query="email lifecycle marketing" --to=.archives/email-ctx.md` — across all wiki packages
- `/wiki get --query="pricing strategies"` — print to stdout

#### Mode 3: Entity-list mode (v4.4 NEW)

Explicit slug list. Each `--entities=<csv>` entry is one of:
- Full spec: `<source-slug>/<type>/<entity-slug>`
- With `--src=<source-slug>`: bare `<type>/<entity-slug>` OR `<entity-slug>` (autoresolved across type folders)

Used internally by Mode 2 (orchestrator passes resolved slugs to script). Also direct ad-hoc use when founder/agent already knows the exact entities.

**Examples:**

- `/wiki get --entities=marketing-management-kotler/concepts/4-Ps-of-marketing,principles-of-marketing-kotler/concepts/market-segmentation-bases` — cross-source explicit bundle
- `/wiki get --src=principles-of-marketing-kotler --entities=market-segmentation-bases,behavioral-segmentation-variables` — bare slugs with source scope

### `/wiki ask "<question>"`

1. **Embed question** — OpenAI `text-embedding-3-small`.
2. **Retrieve** — hybrid search: vector top-K (k=10) + keyword (BM25) join, deduped, scored per Bài #14 ranking (vector*0.5 + keyword*0.3 + backlink*0.2).
3. **Optional rerank** — if `--rerank` flag passed (off by default for cost), call OpenAI rerank model on the top 10.
4. **Synthesize** — invoke `wiki-sync/ask` skill which composes the answer with strict citation discipline (every claim cites a wiki path + chunk anchor; if no citation possible, say "no wiki coverage").
5. **Return** — answer + citation list. NEVER fall back to training data.

### `/wiki audit`

1. **Hash check** — every `ops.knowledge_pages` row's `source_hash` is re-computed from `source_ref`; flag if drift > 0.
2. **Link walk** — every `ops.knowledge_links.target_page_id IS NULL` → orphan.
3. **Dead URL check** — every source RECORD page (`wiki/<source-slug>/source.md`) with `source_kind='url_article'` → HTTP HEAD `source_ref`; flag if 4xx/5xx.
4. **Stale-claim sample** — random 10 % of pages; LLM-evaluate "is this claim still consistent with the source ref?" (cheap sample; full sweep is too expensive).
5. **Write report** — `.archives/wiki-audits/<date>.md` with per-defect file:line precision + total defect rate.
6. **If `--fix`** — for each fix class (orphan, dead, stale), open one PR with proposed remediation.

## Defensive notes

- **Wiki edits are the founder's**. The command writes pages with a `<!-- generated-by: wiki-sync vN -->` marker. Pages WITHOUT this marker (or with it stripped) are treated as founder-edited; re-sync warns and shows a 3-way diff.
- **Re-sync regenerates by default.** Single-source-of-truth: ref = source, wiki = projection. If founder hand-edits a generated page, that's an exception requiring `--merge` (v1.1+) or accepting the warning.
- **All file paths logged to `ops.agent_runs`**. Easy to find "which page came from which ref."
