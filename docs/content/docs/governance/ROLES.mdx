# Vai trò agent & Quyền hạn

> Định nghĩa các vai trò agent vận hành trong `ritsu-works`, mỗi vai trò được phép làm gì, và cách các vai trò ánh xạ tới skill, tool và secrets.

**Chủ sở hữu:** founder
**Cập nhật lần cuối:** 2026-05-02
**Chính sách thay đổi:** PR + founder review. Tier C theo `governance/HITL.md`.

---

## Tại sao vai trò tồn tại

Không có sự phân tách vai trò, lựa chọn duy nhất là "agent có thể làm mọi thứ" hoặc "agent không thể làm gì." Cả hai đều sai.

Vai trò cho phép chúng ta trả lời các câu hỏi như:
- *Tại sao content drafter có thể đọc tài liệu công khai nhưng không thể truy vấn database khách hàng?*
- *Tại sao ETL runner có thể đọc Product Supabase nhưng không bao giờ ghi?*
- *Tại sao support agent có ngân sách LLM khác với growth orchestrator?*

Câu trả lời luôn là: **nguyên tắc đặc quyền tối thiểu.** Mỗi vai trò có khả năng tối thiểu để làm việc của mình. Mọi thứ khác đều bị từ chối.

permissions:

  tier2_schemas_write:   # which schemas it can INSERT/UPDATE

  skills:                # which skills it may invoke
  secrets:               # which secret keys it may access (by name from SECRETS.md)
hitl_max_tier: <A | B | C | D-Std | D-MAX>  # highest tier this role may attempt without escalation
budget:
  monthly_token_usd: <number>      # legacy field; equivalent to economic_budget.monthly_cap_usd
  monthly_tool_calls: <number>     # operational ceiling, separate from cost
economic_budget:
  monthly_cap_usd: <number>        # hard monthly $ cap; budget enforcement uses this
  alert_at_pct: 0.80               # default — Telegram alert at 80%
  escalate_at_pct: 1.00            # default — founder approval at 100%
  hard_block_at_pct: 1.50          # default — block until ROLES.md PR raises cap
  per_task_kind_caps:              # optional; per-instance soft caps for this role's task_kinds
    <task_kind>: <usd_per_instance>
  preferred_models:                # optional; recommended model for this role's tasks
    default: <model_id>
    expensive_tasks: <model_id>    # for blog drafts, deep research
    light_tasks: <model_id>        # for routine reads, classifications
context_budget:
  preamble_tokens: <number>      # max tokens for session-start preamble (CLAUDE.md + role + pillar README)
  working_tokens: <number>       # max accumulated working context before /compact is mandatory
  trigger_compact_at: <0..1>     # fraction of working_tokens at which agent self-invokes /compact
memory_config:
  memory_tool_enabled: <bool>    # Anthropic memory_20250818 tool API; v1.0 default false (Strategy E)
  episodic_recall_enabled: <bool>  # invoke `episodic-recall` skill at task start
  recall_window_days: <int>      # how far back ops.agent_runs is queried
  recall_max_runs: <int>         # how many past runs to load as context (~200 tokens each)
  emit_run_summary: <bool>       # write to ops.run_summaries on completion
  accept_corrections: <bool>     # writes to ops.corrections when founder rejects/edits
notify_on_completion: <bool>     # default Telegram ping after Tier B+ actions
escalation_role: <role slug>     # who to fallback to if this role can't proceed

Xem phần "Hướng dẫn ngân sách context" bên dưới để biết cách đặt các giá trị này.

Các vai trò được định nghĩa dưới dạng file trong `.claude/agents/<role>.md` (định dạng agent của Claude Code). File này là tham chiếu chính sách; file agent là sự khởi tạo runtime.

## Các vai trò, v0.1

Đây là các vai trò ban đầu. Sẽ có thêm khi các pillar lên hoạt động. Trạng thái: ◐ định nghĩa ở đây, ○ file runtime `.claude/agents/<role>.md` chưa được tạo.

### `gps` — General Purpose Steward (Chief of Staff)

Bộ điều phối. Định tuyến công việc tới các vai trò chuyên gia. Vai trò giao tiếp với founder theo mặc định.

```yaml
role: gps
purpose: Receive founder requests, decompose into tasks, route to specialist roles, report back.
home_pillar: cross-cutting
personas_bound: [ceo]    # CEO persona façade resolves to this role (knowledge/workforce-personas.yaml)
permissions:
  tier1_paths:
    - "wiki/**"        # can write reference notes
    - ".archives/**"   # scratch space
    # NO write to 00-charter, governance, pillar SOPs, skills, .claude
  tier2_schemas_read:
    - ops.*            # full read of ops state
    - metrics.*        # full read of mirrored product metrics
  tier2_schemas_write:
    - ops.tasks        # to enqueue work for specialists
    - ops.agent_runs   # to log own actions
  tier3_buckets:
    - ops-transcripts (read+write)
    - ops-artifacts (read)
    - ops-agent-logs (write only — append)
  tier4_namespaces:
    - charter_embeddings (read)
    - skills_embeddings (read)
    - transcripts_embeddings (read)
  mcp_servers:
    - github (read+comment, no merge)
    - telegram (send to founder)
    - supabase-ops (limited to schemas above)
  skills:
    - "*"              # may invoke any skill, but specialists do the work
  secrets:
    - ANTHROPIC_API_KEY
    - GITHUB_TOKEN_READONLY
    - TELEGRAM_BOT_TOKEN
    - SUPABASE_OPS_ANON_KEY  # NOT service key
hitl_max_tier: C
budget:
  monthly_token_usd: 200    # GPS thinks a lot, decomposing
  monthly_tool_calls: 5000
economic_budget:
  monthly_cap_usd: 200
  alert_at_pct: 0.80
  escalate_at_pct: 1.00
  hard_block_at_pct: 1.50
  per_task_kind_caps:
    parent-orchestration: 0.50    # GPS itself shouldn't cost much per orchestration; subagents do the work
    cost-report-query: 0.05
  preferred_models:
    default: claude-sonnet-4-6     # GPS reasoning is cheap; use Sonnet
    expensive_tasks: claude-opus-4-7  # complex multi-pillar decomposition
    light_tasks: claude-haiku-4-5
notify_on_completion: true
escalation_role: founder
```

> **Tại sao GPS không có quyền write trực tiếp tới hầu hết mọi thứ:** nó là router, không phải worker. Nếu chính GPS bắt đầu chỉnh 00-charter hoặc chạy migrations, ranh giới vai trò bị mờ. GPS đề xuất; chuyên gia thực thi (hoặc PR).

- Founder không nên trực tiếp thực hiện các hành động mà một vai trò agent được cấu hình; điều này phá vỡ khả năng quan sát.
- Khi nghi ngờ, founder route qua `gps` để duy trì sự nhất quán pattern.

---

## Hướng dẫn ngân sách context

Mỗi vai trò ở trên có một `context_budget`. Phần này giải thích cách đặt ba số.

**Tại sao ngân sách context tồn tại.** Nền tảng Anthropic cung cấp tiết lộ tiến trình (Skills + subagents) và nén (`/compact`, server-side). Nền tảng KHÔNG THỂ quyết định cho Ritsu *mức độ tích cực* mà mỗi vai trò nên quản lý context — đó là quyết định chính sách của Ritsu. Các vai trò nhẹ, lượng cao (ví dụ `support-agent`) cần các cài đặt khác với các vai trò nặng, suy luận sâu (ví dụ `gps`).

**Ngân sách mặc định theo loại vai trò:**

| Loại | preamble_tokens | working_tokens | trigger_compact_at | Lý do |
|---|---|---|---|---|
| Orchestrator (gps, growth-orchestrator) | 6000 | 80000 | 0.6 | đọc full pillar context; phiên dài |
| Specialist drafter (content-drafter) | 3000 | 30000 | 0.7 | task hẹp; nên compact tích cực |
| Người phản hồi lượng cao (support-agent) | 3000 | 25000 | 0.7 | nhiều ticket ngắn; restart thường xuyên |
| ETL / đường ống dữ liệu (etl-runner) | 2000 | 20000 | 0.8 | chủ yếu là tool calls; context suy luận tối thiểu |
| Triage T&S (trust-safety) | 5000 | 50000 | 0.6 | cần full charter + tham chiếu policy |
| Backoffice (backoffice-clerk) | 4000 | 40000 | 0.65 | quy trình có cấu trúc; chân trời trung bình |
| Code reviewer | 4000 | 50000 | 0.65 | đọc diff; phiên trung-dài |
| Founder | không giới hạn | không giới hạn | 0.85 | tự định đoạt; chỉ trigger khi gần giới hạn |

**Cách `trigger_compact_at` hoạt động.** Khi context làm việc của agent đạt `working_tokens × trigger_compact_at`, agent tự gọi `/compact` với các chỉ dẫn phù hợp với vai trò. Ví dụ cho content-drafter ở 30000 × 0.7 = 21000 tokens working:

```
/compact Preserve: the active draft, the brand_voice citations,
any open HITL approvals. Drop: tool result transcripts, file-search
intermediate steps.
```

**Cách tinh chỉnh.** Cài đặt tháng đầu là các giá trị mặc định bảo thủ từ bảng này. Sau 4 tuần dữ liệu `ops.agent_runs`:

- Nếu một vai trò hiếm khi chạm `trigger_compact_at`, nâng `working_tokens` (cho phép phiên dài hơn trước khi compact)
- Nếu chất lượng của một vai trò suy giảm trước khi compact trigger, hạ `trigger_compact_at` (compact sớm hơn)
- Nếu preamble nhất quán trong 50% của `preamble_tokens`, vai trò không đọc đủ context — điều tra
- Nếu preamble vượt xa `preamble_tokens`, vai trò đọc quá nhiều — chia context, dùng subagents

Các giá trị này là một phần của governance và thay đổi qua PR.

## Hướng dẫn cấu hình memory

`memory_config` của mỗi vai trò đặt thái độ của vai trò hướng tới học hỏi qua các phiên. Kiến trúc đầy đủ được tài liệu hóa trong `knowledge/memory-architecture.md` — phần này là hướng dẫn vận hành để điền các giá trị vai trò.

**Strategy E baseline (v1.0):** tất cả các vai trò sử dụng episodic recall (Type 2 memory: `ops.agent_runs`); không vai trò nào sử dụng memory tool API (Type 3 file memory). Lý do và chi tiết quyết định nằm trong `_build/notes/problem-4-memory-learning-loop.md`.

**Giá trị mặc định theo loại vai trò:**

| Loại | memory_tool | recall_window_days | recall_max_runs | emit_run_summary |
|---|---|---|---|---|
| Orchestrator (gps, growth-orchestrator) | false | 90 | 5 | true |
| Specialist drafter (content-drafter) | false | 60 | 3 | true |
| Người phản hồi lượng cao (support-agent) | false | 30 | 5 | true |
| ETL / đường ống dữ liệu (etl-runner) | false | 7 | 2 | true |
| Triage T&S (trust-safety) | false | 180 | 5 | true |
| Backoffice (backoffice-clerk) | false | 90 | 3 | true |
| Code reviewer | false | 60 | 3 | true |
| Founder (con người) | n/a | n/a | n/a | n/a |

**`memory_tool_enabled: true` là thay đổi D-Std** — cần nghi thức PR cộng với use case được tài liệu hóa cho trạng thái file-based đa ngày mà episodic recall không thể phục vụ. Tính đến spec v1.0, không vai trò nào đáp ứng tiêu chuẩn này. Đánh giá lại khi brainstorm Bài #5 (Multi-Agent Orchestration) hoàn thành.

**Tinh chỉnh `recall_window_days`.** Bắt đầu với mặc định. Sau 4 tuần dữ liệu `ops.agent_runs`:
- Nếu các recall của một vai trò nhất quán chỉ hiển thị các run trong 7 ngày qua (các run cũ hơn không liên quan), thu nhỏ `recall_window_days`
- Nếu các recall trả về \< 3 kết quả thường xuyên (lịch sử thưa thớt), mở rộng `recall_window_days`
- Nếu một vai trò thường xuyên đối mặt với tình huống mới không được bao phủ bởi các recall, hiệu chỉnh lại `recall_max_runs` lên — nhưng theo dõi chi phí (mỗi recall tốn ~200 tokens × max_runs)

**Tác động ngân sách của `recall_max_runs`.** Mỗi recall row là ~200 tokens bao gồm run_summary. 5 recalls = ~1K tokens thêm vào preamble của mỗi task. Qua hàng nghìn task/tháng, đây là chi phí thực. Đặt bảo thủ; chỉ tăng khi giá trị được chứng minh.

**`emit_run_summary: true`** là mặc định cho hầu hết các vai trò. Tóm tắt hậu kỳ ~150 token là thứ làm cho episodic recall hữu ích cho các phiên KHÁC sau này. Vô hiệu hóa nó chỉ có ý nghĩa cho các vai trò tần suất rất cao nơi chi phí tóm tắt vượt quá giá trị học hỏi (đánh giá lại nếu etl-runner chạy > 1000 lần/ngày, chẳng hạn).

**`accept_corrections: true`** là mặc định. Khi founder từ chối hoặc chỉnh output của agent, runtime ghi lý do vào `ops.corrections`. Các recall tương lai sẽ hiển thị các bản này. Vô hiệu hóa chỉ cho các vai trò mà correction là vô nghĩa (ví dụ, ETL chỉ đọc).

## Vòng đời vai trò

Khi cần một vai trò mới:

1. Mở PR thêm vào file này (hành động Tier C).
2. Thêm cấu hình runtime trong `.claude/agents/<role>.md`.
3. Nếu cần secrets mới, cập nhật `governance/SECRETS.md`.
4. Nếu cần MCP server mới, cập nhật `mcp/servers.yaml` (hành động Tier C).
5. Nếu cần bảng/bucket mới, cập nhật `knowledge/manifest.yaml` và `knowledge/schemas/`.
6. Cần sự chấp thuận của founder (HITL (Human-in-the-Loop) Tier C).

Khi loại bỏ một vai trò:

1. Loại khỏi luân phiên đang hoạt động bằng cách chỉnh `.claude/agents/<role>.md` thành `status: deprecated`.
2. **Đừng xóa** trong ≥ 90 ngày — các `agent_runs` quá khứ tham chiếu vai trò; xóa phá vỡ truy nguyên audit.
3. Sau 90 ngày, lưu trữ file agent vào `.archives/deprecated-roles/<role>-<date>.md` và xóa khỏi cấu hình hoạt động.

## Khi một vai trò chạm ngân sách

Theo `knowledge/economic-architecture.md` Trục 2, hook `pre-llm-call-budget` thực thi leo thang 3 tầng so với `economic_budget.monthly_cap_usd`:

- **80% (`alert_at_pct`)** — vi phạm đầu tiên đăng cảnh báo qua Telegram: "Growth-orchestrator ở 80% ngân sách hàng tháng ($240 trên $300). Còn 6 ngày trong tháng." Các call tiếp theo trong cùng tháng được cho phép mà không cảnh báo lại (tránh mệt mỏi thông báo).

- **100% (`escalate_at_pct`)** — mọi LLM call thêm bị TẠM GIỮ; cần sự chấp thuận của founder qua Telegram. Founder có thể chấp thuận từng cái, hoặc tạm thời nâng cap cho phần còn lại của tháng qua lệnh inline.

- **150% (`hard_block_at_pct`)** — trần cứng. Không có tùy chọn chấp thuận của founder từ chính hook. Để vượt 150%, founder phải mở PR cho file này (nghi thức Tier C theo HITL.md) nâng `monthly_cap_usd`. Điều này bảo vệ chống mệt mỏi chấp thuận và buộc điều tra khi sử dụng đang lệch cấu trúc khỏi mục tiêu.

Các cap mềm per-task-kind (`per_task_kind_caps`) hoạt động độc lập: ngay cả khi ngân sách hàng tháng khỏe, một instance task đơn lẻ có chi phí ước tính vượt cap task_kind của nó sẽ leo thang. Điều này bắt chế độ thất bại "single bug looped task".

Ngân sách reset vào ngày 1 mỗi tháng lúc 00:00 UTC.

Đối với các đợt tăng đột biến hợp lệ ad-hoc (sự kiện ra mắt, chiến dịch nội dung), founder có thể nâng cap trước qua PR Tier C trước khi đợt tăng bắt đầu. Điều này được ưu tiên hơn các chấp thuận phản ứng trong đợt tăng.

Giai đoạn hiệu chỉnh 30 ngày (sau khi ra mắt v1.0) đặt thực thi ở chế độ chỉ cảnh báo ban đầu. Thực thi 3 tầng đầy đủ kích hoạt ngày 14. Xem `knowledge/economic-architecture.md` "30-day calibration discipline" để biết lịch trình chính xác.
