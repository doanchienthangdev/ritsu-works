### Các hệ thống khác (đã bảo lưu)

Khi bất kỳ hệ thống nào sau đây trở nên hoạt động, file này được cập nhật qua PR:

- HubSpot (CRM) — các API token per-role

## Tại sao kênh thuộc thương hiệu vẫn chỉ founder

Twitter/LinkedIn/YouTube v.v. là các kênh thuộc thương hiệu với sự tích lũy danh tiếng. Một compromise trên những kênh này ảnh hưởng trực tiếp đến thương hiệu công ty — phạm vi tác động khác với các bot GitHub nội bộ.

Đối với v1.0:
- Agent (ví dụ, growth-orchestrator) SOẠN bài đăng trong `.archives/drafts/`
- Founder review qua Telegram (HITL (Human-in-the-Loop) Tier C theo `governance/HITL.md`)
- Founder đăng thủ công bằng credential riêng của founder
- ops.agent_runs ghi lại tác giả bản nháp

Sau v1.0, khi các pattern chứng minh là an toàn, đăng tự động có thể được thêm với các bot per-channel riêng biệt. Mỗi lần thêm = D-Std PR theo file này.

## Danh sách kiểm tra cấp phát định danh (khi thêm vai trò mới)

Theo nghi thức thêm vai trò trong Bài #2:

1. ☐ Tài khoản bot GitHub được tạo bởi founder (`ritsu-{role}-bot`)
2. ☐ Tạo email forwarder (`{role}@ritsu.ai`)
3. ☐ Khóa API Anthropic được tạo với cap ngân sách
4. ☐ Chính sách Supabase RLS được thêm nếu vai trò có DB write
5. ☐ Tất cả secrets được lưu trong trình quản lý secrets theo `governance/SECRETS.md`
6. ☐ File này (`IDENTITY.md`) được cập nhật với mapping mới
7. ☐ `governance/ROLES.md` được cập nhật với định nghĩa vai trò
8. ☐ `governance/SECRETS.md` được cập nhật với các tên secret
9. ☐ Tạo file runtime `.claude/agents/{role}.md`
10. ☐ Tests hooks pass (`pre-tool-secrets` nhận ra vai trò mới)

PR bao gồm TẤT CẢ các thay đổi trên. Nguyên tử.

## Danh sách kiểm tra ngừng định danh (khi loại bỏ vai trò)

1. ☐ Đánh dấu vai trò `status: deprecated` trong `governance/ROLES.md`
2. ☐ Thu hồi tất cả secrets tại trình quản lý secrets
3. ☐ Lưu trữ (KHÔNG xóa) tài khoản bot GitHub — bảo tồn lịch sử commit
4. ☐ Vô hiệu hóa email forwarder (các email hiện tại được chuyển đến founder)
5. ☐ Đặt khóa API Anthropic ở trạng thái disabled
6. ☐ Cập nhật file này đánh dấu row là `status: deprecated YYYY-MM-DD`
7. ☐ Sau 90 ngày, làm sạch audit: xác nhận không có tham chiếu trong code/skills, sau đó xóa row (bảo tồn trong git history)

Loại bỏ là D-Std PR.

## Tần suất audit

Hàng quý (theo `governance/SECRETS.md`):

1. **Đối chiếu:** mỗi secret trong file này có tồn tại trong trình quản lý secrets không? Mỗi secret trong trình quản lý có entry ở đây không?
2. **Kiểm tra hoạt động:** mỗi bot per-role có hoạt động gần đây theo mục đích sử dụng dự kiến của nó không? Các bot ngủ được đánh dấu.
3. **Kiểm tra quyền:** phạm vi bot GitHub khớp với bảng không? Email DKIM vẫn hợp lệ không?
4. **Quét compromise:** bất kỳ hoạt động bất thường nào trong `ops.agent_runs.secrets_accessed` không? Bất kỳ vai trò nào truy cập secrets nó không nên không?

Output: báo cáo audit hàng quý trong `.archives/audits/identity-{YYYY-Q}.md`. Các mục thất bại trở thành PR.

## Các anti-pattern cần từ chối

- **"Sử dụng lại một bot GitHub cho hai vai trò mới."** Không — phá vỡ mục đích gán per-role. Thêm một bot mới.
- **"Bỏ qua cấp phát email cho `code-reviewer`, nó không gửi gì cả."** Đúng — nhưng vẫn ghi lại "không có khả năng gửi" trong file này là `n/a`. Các agent tương lai tra cứu bảng cần thấy "không có gì rõ ràng."
- **"Founder đăng lên Twitter qua agent ở v1.0 để tiết kiệm thời gian."** Không — kênh thương hiệu vẫn do founder kiểm soát cho đến khi pattern được chứng minh là an toàn. Đánh giá lại sau v1.0.
- **"Email đối khách hiển thị `support-agent` là người gửi."** Không — tên hiển thị là "Ritsu Assistant" theo sub-domain C. Sự gán nội bộ được bảo tồn riêng.
- **"Thêm truy cập hệ thống mới mà không cập nhật file này."** Không — PR nguyên tử hoặc rollback. Trôi dạt giữa mapping và thực tế là chế độ thất bại cốt lõi mà file này ngăn chặn.
